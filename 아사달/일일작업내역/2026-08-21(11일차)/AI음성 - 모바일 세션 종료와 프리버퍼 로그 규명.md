# 모바일 세션 종료와 프리버퍼 로그 규명

> [!summary] 한 줄 요약
> 모바일에서 마이크가 저절로 꺼지는 원인이 프론트의 `pagehide` 즉시 release 임을 밝혀 유예 방식으로 고치고, dev 로그의 프리버퍼 경고 78건이 **전 세션 100% 발생하는 구조적 노이즈**임을 실측으로 확정해 정리했다. 프로젝트: [[AI음성]]

## 마이크가 저절로 꺼지는 문제 — 프론트가 스스로 종료를 보내고 있었다

증상은 "모바일에서 음성채팅 중 마이크가 자동으로 비활성화됨"이었다. 세션 관리와 연관돼 있냐는 질문에서 출발해 프론트 이벤트 체인을 따라간 결과, **서버가 아니라 프론트가 원인**이었다.

`webrtc_voice_module.js` 생성자에 이 배선이 있었다.

```js
// pagehide는 모바일에서 beforeunload보다 신뢰도가 높다.
this._boundReleaseOnPageHide = () => this.releaseServerSession();
window.addEventListener('pagehide', this._boundReleaseOnPageHide);
```

의도는 "탭을 닫으면 서버 세션을 정리"였는데, **모바일 브라우저는 페이지가 닫히지 않는 상황에서도 `pagehide` 를 던진다** — 앱 전환, 화면 잠금, 알림 확인, 탭 전환, bfcache 진입 전부 해당한다.

연쇄는 이렇게 이어졌다.

```
앱 전환/화면 잠금
 → pagehide → releaseServerSession()  (keepalive: true 라 백그라운드에서도 전송)
 → 서버 close(session_id)             ← generation 없이 무조건 정리
 → 복귀 시 connectionState = 'failed'
 → disconnect() → track.stop()        ← 마이크 비활성화
```

핵심은 세 번째 줄이다. release 엔드포인트는 "사용자가 명시적으로 끝냈다"는 전제라 **유예도 확인도 없이 즉시** 정리한다. 잠깐 화면을 껐다 켠 것과 통화를 끝낸 것을 서버가 구분할 방법이 없다.

### 서버의 정리 장치들은 무고했다

서버에 있는 다른 종료 경로는 전부 유예를 두고 있어 모바일 잠깐 이탈로는 발동하지 않는다. **프론트가 스스로 "끝내주세요"를 보내는 바람에 이 유예 장치들이 개입할 기회조차 없었다.**

| 경로 | 조건 | 잠깐 이탈에 발동? |
|---|---|---|
| ICE disconnected | 30초 유예 후에도 disconnected 일 때만 | 아니오 |
| 무프레임 좀비 판정 | 오디오 60초 없음 | 아니오 |
| 좀비 스위퍼 | 60초 주기, 120초 미연결 | 아니오 |
| **release 엔드포인트** | **즉시, 무조건** | **예** |

### 수정 — 즉시 종료를 유예 종료로

`beforeunload`(실제 이동·닫기)만 즉시 정리하고, `pagehide`·백그라운드 전환은 유예 타이머로 돌렸다. 복귀하면 취소한다.

| 이벤트 | 이전 | 수정 후 |
|---|---|---|
| `beforeunload` | 즉시 release | 즉시 release (유지) |
| `pagehide` | 즉시 release | **60초 유예 예약** |
| 백그라운드 전환 | 처리 없음 | 유예 예약 |
| 복귀(`pageshow`·visible) | — | **타이머 취소** |

유예 중 페이지가 진짜로 죽으면 타이머도 사라지지만, 서버의 3중 정리 장치가 수거하므로 좀비 세션은 생기지 않는다. bfcache 복귀 직후 타이머가 먼저 깨는 경우를 대비해 실행 시점에 `visibilityState` 를 다시 확인한다. `connect()`·`disconnect()`·`destroy()` 에도 타이머 취소를 넣어 이전 세션의 타이머가 새 세션을 죽이지 않게 했다.

수정 파일은 프론트 `webrtc_voice_module.js` 한 개이고, `node --check` 문법 검증을 통과했다.

## 프리버퍼 경고 78건 — 전 세션 100% 타임아웃, 구조적 노이즈였다

"AI 목소리가 끊긴다 / AI가 내 말을 못 알아듣는다" 두 증상의 근거를 찾으려 dev 로그를 뒤지다 발견했다.

```
⚠️ [PROXY-UP] 지터 버퍼 프리버퍼 타임아웃(buffered=0/4, timeout=1.00s)
```

**모든 로그가 예외 없이 `buffered=0/4`** 였다. "4개 중 3개는 왔는데 부족"한 경계 사례가 하나도 없다는 것이 이상해 성공/실패 개수를 비교했다.

| 항목 | 개수 |
|---|---|
| 프리버퍼 성공(`🎧 지터 버퍼 준비`) | **0** |
| 프리버퍼 타임아웃 | **78** |

**성공률 0%.** 일부 세션의 연결 불량이라면 섞여야 하는데 단 한 번도 성공한 적이 없다 → 네트워크가 아니라 구조적 타이밍 문제로 확정됐다.

### 메커니즘

```
게이트 트랙을 PC②(→OpenAI)에 addTrack
 → OpenAI 송신기가 첫 프레임을 당김 → recv()
 → _ensure_reader_started()   ← 리더 루프가 이때 처음 뜬다
 → _wait_for_prebuffer()      ← 곧바로 4프레임(80ms)을 1초간 대기
 → 그런데 브라우저↔서버 ICE·DTLS 가 아직 안 끝나 마이크 RTP 미도착
 → 1초 뒤 buffered=0/4 로 포기
```

**"프레임을 기다릴 준비"가 "프레임이 흐르기 시작"보다 항상 먼저** 일어난다. 서버가 OpenAI 와 붙는 속도가 브라우저와 붙는 속도보다 빠르기 때문이다.

### 피해는 작지만 로그 오염이 컸다

| 항목 | 실제 영향 |
|---|---|
| 세션 시작 1초 정체 | 사용자는 대개 그때 말하지 않으므로 발화 유실은 없음 |
| 타임아웃 후 | 무음 프레임을 내보내다 진짜 오디오가 오면 정상 전환 — 자동 복구 |
| 통화 중 끊김 | **무관** (프리버퍼는 세션당 1회) |
| 운영 로그 | **전 세션 WARNING** — 진짜 신호(업링크 언더플로·좀비 종료)를 덮고 있었다 |

마지막 항목이 실질적으로 가장 큰 해악이었다. 같은 로그에 있던 진짜 이상 신호들이 이 78건에 묻혀 있었다.

### 수정 — 대기 단축 + 경고 분리

```
prebuffer_timeout_sec  1.0 → 0.2      세션 시작 정체를 5분의 1로
buffered == 0          → debug        "스트림 미시작" (전 세션 공통, 정상)
buffered 1~3           → warning      "지터 부족" (진짜 이상)
```

**적용 범위는 업링크뿐이다.** 다운링크는 `v3/audio_tracks.py` 의 `AudioProxyTrack` 을 쓰고(`server_webrtc:62`), 이번에 고친 `v4/audio_tracks.py` 의 기반 클래스는 게이트만 상속한다 — 커밋 전에 import 경로로 확인했다.

## 부수 확인 — AI 목소리 끊김은 서버 구간이 아니다

같은 로그에서 다운링크(`[PROXY]`) 언더플로는 이틀간 **2건, 둘 다 count=1** 이었다. 무음 프레임 1개(20ms)로 사람이 인지할 수 없는 수준이다. 폐기(`dropped=`)는 아예 측정되지 않았는데, 그 카운터가 30,000프레임(약 10분) 주기 상태 로그에만 실려 짧은 통화에서는 찍히지 않기 때문이다.

즉 **서버 다운링크 버퍼가 원인이라는 증거는 없다.** 남은 용의자는 서버↔브라우저 RTP 손실이나 모바일 브라우저 재생 쪽이며, 확인하려면 폐기 카운터 계측(상태 로그 주기 단축 또는 진단 엔드포인트)이 필요하다.

반면 **업링크는 실제로 끊기고 있다.** 세션 시작 프리버퍼 0건 외에도 통화 중 언더플로가 반복됐고, 한 세션은 60초 연속 무프레임으로 좀비 판정되어 종료됐다.
