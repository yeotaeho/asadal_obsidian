# 음성채팅기록 녹음기 PairRecorder

> [!summary] 한 줄 요약
> 질문 구간과 그 뒤 들린 답변을 한 쌍으로 메모리에 모으고, 짝이 맺어지고 답변이 끝나면 저장소에 쓰기를 넘기는 **녹음기 본체를 독립 모듈로** 테스트 우선 작성했다. `feat/voice-record` `a236d5f`, **328 → 342 passed**. 통화 경로 연결은 1단계 main 반영 뒤. 기능: [[음성채팅기록]]

## 무슨 작업

설계서 §5.2~5.4 의 녹음 규칙을 1단계 코드에 의존하지 않는 모듈로 만들었다. 입력은 프레임 바이트와 이벤트뿐이고 파일은 만지지 않는다.

```
feed_uplink(pcm, rate, ch)     B 프레임 → 모노 24kHz → 링버퍼(5초), 열린 질문에 이어 붙임
speech_started(item, ms, turn) 링버퍼에서 ms 위치부터 질문 열기, 앞 쌍의 답 수집 끝(끼어들기)
speech_stopped(item, ms)       ms 위치에서 질문 닫기 → 쌍 생성, 답 수집 시작
playback_started / drained     재생 창 열고 닫기
feed_downlink(pcm, rate, ch)   창이 열린 동안 수집 중인 쌍의 답에 붙임
farewell_started               답 수집 끝 (종료말은 담지 않음)
resolve(item)                  짝 맺음 → 같은 턴 질문 합치고 경로·토큰 반환
abandon(item) / close()        폐기 / 짝 맺은 쌍만 들린 데까지 쓰고 종료

저장 조건(한 곳): 짝 맺음 && (답 끝 || 재생 창 닫힘) — 순서 무관
```

## 왜

OpenAI 가 주는 `audio_start_ms`·`audio_end_ms` 가 B 스트림 기준이라 링버퍼에서 바이트 위치로 바로 자를 수 있다. 확인해 보니 **이 오프셋을 읽는 코드가 지금까지 한 곳도 없었다.** 설계의 핵심 가정이 한 번도 쓰인 적 없다는 뜻이라, 연결 뒤 첫 dev 통화에서 오디오 탭 B 파일과 대조하는 검증을 가장 먼저 둔다.

프레임 형식은 오디오 탭 기록기가 쓰는 방식(`to_ndarray().tobytes()`, s16 인터리브, 보통 48kHz 스테레오)을 따랐다. `AudioFrame` 변환은 연결 때 훅이 맡아, 녹음기는 프레임 객체 없이 테스트된다.

## Codex 리뷰 판단

| 지적 | 판단 |
|---|---|
| P1 통화 경로에 연결 안 됨 | 단계 분할의 결과, 미반영. 연결 지점(resolver·폐기 알림)이 1단계 브랜치에만 있다 |
| P1 도구 턴에서 한마디 재생이 끝나기 전에 짝이 맺어지면 중간 drain 에서 써져 최종 답이 빠진다 | **전제가 실제 통화에서 생기지 않아 미반영.** 도구 호출 응답은 1단계 기록기가 짝에서 제외하므로 짝은 도구 후속 답변의 `response.done`(두 번째 창이 이미 열린 뒤)에 맺어진다. 늦은 전사는 대기열에서 같은 시점을 기다리거나, 대기 상태에 도착해 도구가 취소·폐기된다. 예외는 잡음 답변이 남는 기존 문제뿐이고 그땐 글도 틀린다. **연결 때 기록기+녹음기 도구 턴 통합 테스트로 계약 고정** |
