# WebRTC·WS 구간 정리와 전화상담 연결 방식

> [!summary] 한 줄 요약
> "WebRTC 는 빠르다는 것 말고 이점이 없지 않나, 음성채팅은 WS·전화상담은 WebRTC 인가" 라는 질문을 조사했다. **답은 구간마다 다르다.** 서버↔OpenAI 는 WS 가 맞고, 브라우저↔서버는 WebRTC 를 유지하는 게 맞다. 전화상담은 WebRTC 가 아니라 **전화망 SIP** 이고, 뒤쪽 AI 연결은 결국 WS 로 모인다. 코드 변경은 없다. 기능: [[AI음성]]

## 무슨 작업

브라우저 구간의 WebRTC 이점, 전화상담 연결 구조, 통신사가 어디까지 라우팅하는지를 조사했다.

| 구간 | 권장 | 이유 |
|---|---|---|
| 브라우저↔서버 | **WebRTC 유지** | 나쁜 망에서도 실시간을 유지한다. 재생 지터버퍼·손실 은닉·Opus·에코 제거 연동이 브라우저에 들어 있다. 프론트가 도메인 약 700개 FTP 사본이라 전송 방식 교체 비용이 크다 |
| 서버↔OpenAI | **WS 전환** | OpenAI 가 서버 간 연결에 WS 를 권한다. 중계 지터버퍼 손실 구조가 사라진다 |
| 전화 | **SIP**(통신사 쪽) | 전화망은 SIP 신호 + RTP 음성(G.711 8kHz)이다. WebRTC 가 아니다 |

## 전화상담 연결 3안

```
A. OpenAI SIP 직결
   전화 → 통신사/트렁크 → sip:proj_…@sip.api.openai.com;transport=tls
   → 웹훅 realtime.call.incoming → 우리 서버가 REST 로 수락(세션 설정)
   → 같은 통화에 WS(call_id)로 붙어 도구·RAG·종료 제어. 상담원 연결은 refer
   음성이 우리 서버를 안 거친다(v3 와 같은 구조)

B. CPaaS 미디어 스트림
   전화 → Twilio 등 → WS(G.711 base64) → 우리 서버 → WS(audio/pcmu) → OpenAI
   음성이 우리 서버를 거친다(v4 와 같은 구조). BVC·이벤트 판정을 넣을 수 있다

C. 자체 교환기
   전화 → 국내 SIP 트렁크 → Asterisk/FreeSWITCH → 우리 서버 → WS → OpenAI
   B 를 직접 운영. RTP 용 UDP 포트 개방이 필요하다
```

세 안 모두 우리 서버와 OpenAI 사이는 WS 다. 그래서 서버↔OpenAI WS 전환이 전화상담의 공통 기반이 된다.

## 통신사가 해 주는 것

통신사는 **번호에서 우리 SIP 수신 지점까지** 라우팅한다. 그 뒤의 AI 연결은 우리 몫이다. 통신 3사 모두 기업 인터넷전화·SIP 트렁크 상품이 있다. 국내 트렁크가 해외 OpenAI SIP 로 TLS 를 바로 보내 주는지는 불확실해 SBC·교환기나 CPaaS 를 사이에 두는 게 일반적이다(확인 필요).

Twilio 는 한국 지역·수신자부담 번호 수신을 지원한다. 규제 서류(법인인감증명서 또는 대표자 신분증 등)가 필요하고, 수신자부담 번호는 수신 전용이며, 발신번호 표시는 보장되지 않는다. Twilio 트렁크를 OpenAI SIP 에 잇는 공식 가이드가 있다.

## 전화가 음성채팅과 다른 점

| 항목 | 음성채팅(브라우저) | 전화 |
|---|---|---|
| 음질 | 48kHz | G.711 8kHz 협대역 |
| 에코 제거 | 브라우저 | 전화기 단말 |
| 잡음·타인 목소리 | BVC 서버 배치 | Krisp 전화용 모델(`krisp-viva-tel`, 16kHz 이하) |
| 추가로 필요한 것 | — | 번호·트렁크 계약, 녹음 고지, 상담원 연결, DTMF |
