# 사투리 모드 dev 통화 검증

> [!summary] 한 줄 요약
> dev(`feat-dialect-glossary-dev` → dev #61)에서 test.han.kr 여태호 봇으로 세 번 통화해 **VITO 전사 → realtime 음성 답변 경로가 끝까지 동작함**을 확인했다. 통화 1 에서 문장 앞부분이 빠진 원인도 찾았다. **배포 직후 첫 RAG 검색에서 tiktoken 을 동기로 불러오느라 이벤트 루프가 8.8초 멈췄고**, 그동안 업링크 270패킷이 버려졌다. 기능: [[사투리 인식]]

## 무슨 작업

브라우저 마이크에 직접 말할 수 없어서, 브라우저와 같은 방식으로 붙는 aiortc 클라이언트로 dev 에 통화를 걸었다. 경로는 `/voice/dev/voice-chat-v4/agent/session`, `testchatbot1`, 봇 `d98598b0-…-db9af4d86cb4` 다. 마이크 대신 AI Hub 경상 녹음 3개(6~7초)를 실시간 속도로 흘렸다. 서버가 브라우저 채널로 보내는 이벤트와 dev 서버 로그를 대조했다.

| 통화 | 켠 방법 | 세션 | 결과 |
|---|---|---|---|
| 1 | 요청 `stt_engine: "vito"` | `4241e15d` | 3턴 모두 응답. 2번째 발화 앞부분 빠짐 |
| 2 | 요청 `stt_engine: "vito"` | `883fe37c` | 3턴 모두 정상 |
| 3 | 요청에 없음 (`.env` `VOICE_STT_VITO_BOTS`) | `73301b50` | 3턴 모두 정상. **봇 목록 방식도 동작** |

통화 2 기준으로 정답·전사·답변을 나란히 보면 다음과 같다.

| 정답 | VITO 전사 | AI 답변 |
|---|---|---|
| 옛날부터 조상꿈이나 돼지꿈 꾸만 … 좋아 해찌로 | 옛날부터 조산꿈이나 돼지꾼꿈만 … 조해지로 | 좋은 징조로 해석된다고 답함 — **뜻을 알아들음** |
| 오랫동안 … 할무닌데 도라가주씨 매매 아프네요 | … 한미인제 **도석간에** 매매 아프네요 | "말이 끊겨 의미 파악이 어렵다" — '돌아가셔서' 를 못 받아 적음 |
| 혈압약은 시간을 맞춰 … 안 그러면 효과가 없습니다 | 시간을 **맞추가** … 안 **그라면** 효과가 없습니다 | 같은 시간 복용이 중요하다고 **정확히 답함** |

**발화 끝 → 전사 도착은 약 1.2초** 로 로컬 실측과 같았다. 대신 모델이 세 질문 모두 먼저 "근거를 확인해 볼게요" 라고 말한 뒤 검색 도구를 불러, 실제 답변은 전사 후 **5~8초** 뒤에 나왔다. 통화 1 에서는 검색이 시간 초과로 실패했다고 답했다.

## 왜 — 앞부분 누락 분석

통화 1 의 두 번째 발화("오랫동안 한 동네에서 … 매매 아프네요")는 전사가 `인제 도서서 가에 매매 아프네요` 한 건으로만 왔다. 해당 구간 서버 로그를 받아 원인을 확정했다. **사투리 모드 문제가 아니라, 배포 직후 첫 RAG 검색이 서버 이벤트 루프를 약 8.8초 멈춘 것**이다.

```
01:19:09.859  QueryEnrichment (첫 검색 시작 — 컨테이너 배포 후 첫 search_knowledge_base)
              ─── 8.8초 동안 로그 0줄 (평소 RTP 통계가 1초마다 찍힘) ───
01:19:18.669  tool 호출 타임아웃(timeout=5.0s)   ← 5초 타이머가 13.8초 만에 발동 = 루프 정지
01:19:19.67   RTP 통계[브라우저] lost=270  window_loss=54.9%  jitter=1114ms  (품질 경고)
              RTP 통계[OpenAI]   lost=271  window_loss=55.3%
              PROXY-DOWN dropped 0 → 117
01:19:23.720  [VITO] 최종 전사 = 뒷부분만   ← 재연결 없음, 연결은 세션당 1회
```

루프가 멈춘 동안 브라우저가 보낸 업링크 RTP 약 270패킷(20ms 단위로 약 5.4초)이 서버에서 버려졌다. 그래서 VITO 는 발화 앞부분을 받지 못했다. OpenAI 로 가는 다운링크도 같은 수만큼 잃었다(답변 소리 끊김, `dropped=117`).

루프를 막은 것은 LangChain `OpenAIEmbeddings` 의 첫 `aembed_query` 다. 토큰 길이 검사를 위해 tiktoken 인코딩을 **동기로** 불러오는데, 캐시가 없으면 인터넷에서 내려받는다. 로컬 재현 결과는 다음과 같다.

| 조건 | 첫 호출 | 이벤트 루프 최대 멈춤 |
|---|---|---|
| tiktoken 캐시 없음 (배포 직후 컨테이너) | 3.80초 | **3.15초** |
| 캐시 있음 | 0.56초 | 0.14초 |

dev 서버에서는 8.8초였다. 내려받기 경로의 네트워크가 더 느린 것으로 보이며, 이 차이는 따로 재지 않았다. 통화 2·3 은 캐시가 생긴 뒤라 검색이 정상이었고 누락도 없었다.

**영향 범위는 사투리 모드에 한정되지 않는다.** 배포나 재시작 뒤 첫 검색 한 번이, 단일 프로세스의 **모든 통화**를 수 초씩 멈춘다. 기본 v4 에서는 그 사이 OpenAI 로 가는 업링크가 끊긴다. 운영도 배포할 때마다 한 번씩 겪는 구조다.

해결 후보는 다음과 같다. 아직 어느 것도 적용하지 않았다.

| 안 | 내용 | 수정 범위 |
|---|---|---|
| 시작 시 예열 | 앱 기동 때 임베딩 객체 생성과 tiktoken 인코딩 로드를 한 번 해 둔다 | `ai_voice/` 또는 `main.py` (루트는 사전 확인 필요) |
| 이미지에 캐시 포함 | Dockerfile 에서 `tiktoken.get_encoding("cl100k_base")` 를 실행하고 `TIKTOKEN_CACHE_DIR` 를 고정한다 | `Dockerfile` (사전 확인 필요) |
| 길이 검사 끄기 | `check_embedding_ctx_length=False` 로 tiktoken 을 아예 쓰지 않는다 | shim `chat/faiss_process.py` (사전 확인 필요). 긴 입력 분할이 사라짐 |
