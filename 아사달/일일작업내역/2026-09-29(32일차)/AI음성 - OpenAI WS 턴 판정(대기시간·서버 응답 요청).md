# OpenAI WS 턴 판정(대기시간·서버 응답 요청)

> [!summary] 한 줄 요약
> WS 세션은 게이트로 소리를 붙들지 않고, 대기시간을 끼어들기 판정에 쓰며, 응답 요청을 서버가 보낸다. 재현 시험에서 조용할 때 "네"에 답하고 끼어들기가 **0.7초** 빨라졌지만, 서버 응답 요청이 턴마다 **0.31초** 더 걸렸다. 기능: [[OpenAI WS 전송]]

## 무슨 작업

사용자가 A안(소리는 흘리고 대기시간은 판정으로)과 `create_response=false` 를 골랐다. WS 세션에서는 OpenAI 의 끼어들기·자동 응답을 끄고 말 감지·전사만 맡긴다. 턴 판정은 `OpenAIWsChannel` 이 한다.

| 상황 | 판정 | 동작 |
|---|---|---|
| AI 가 조용할 때 한 말 | 받는다. 말소리 비율(게이트 관문)이 모자란 소리만 거른다 | 확정(committed)되면 `response.create` |
| AI 차례(생성·재생·도구 대기)에 들린 말 | 끼어들기 후보로 붙든다. 브릿지는 모른다 | 대기시간 동안 게이트 3관문을 넘기면 생성 취소·소리 버림·들려준 만큼 자르기 뒤 말 시작을 알린다 |
| 대기시간 전에 끝난 말 | 없던 일 | 항목 삭제, 늦게 온 전사도 숨김 |
| 대기시간 미사용 봇 | 말 시작 즉시 끼어든다 | WebRTC 의 `interrupt_response` 와 같다 |

업링크는 게이트 트랙 대신 `UplinkAudioProxyTrackV4` 원음을 보낸다. 녹음·화자 판정 훅은 그대로 걸린다. 브릿지에는 OpenAI 가 자동으로 처리한 것처럼 보이므로 브릿지 턴 코드는 고치지 않았다.

재현 시험 도구 `ws_turn_replay.py` 를 새로 만들었다. 합성음을 실제 OpenAI WS 세션에 흘리고, 채널이 브릿지로 내보낸 이벤트로 끊김과 응답 여부를 채점한다.

## 결과

| 시나리오(대기시간 1.2초) | 기준선(1차: 게이트 + 자동) | 2차(턴 판정) |
|---|---|---|
| AI 말 중 기침 0.35초 | 안 끊김·무응답 | 안 끊김·무응답 |
| AI 말 중 "네" 0.7초 | 안 끊김·무응답 | 안 끊김·무응답(항목 삭제) |
| AI 말 중 질문 3.9초 | 입력 **2.4초** 뒤 끊김, 답함 | 입력 **1.7초** 뒤 끊김, 답함 |
| AI 말 중 다른 목소리(TV) | 끊김, 답함 | 끊김, 답함 (화자 판정 연결 전) |
| 조용할 때 "네" 0.7초 | **무응답**(게이트가 버림) | **답함** |
| 조용할 때 문 닫는 소리 | 무응답 | 무응답 |

응답 요청을 서버가 보내면 커밋부터 `response.created` 까지 중앙값 **310ms**(9회)가 더 걸렸다. 자동 응답은 0ms 였다(14회). OpenAI 까지 한 번 왕복하는 시간이고, 자르기 요청→`truncated` 도 300ms 였다. 전략 설명 때 0.06초라고 한 추정은 틀렸다.

발화 끝부터 말 끝 판정(`speech_stopped`)까지는 semantic_vad(eagerness low)가 1.3~2.4초를 썼다. 이 구간이 응답 지연에서 가장 크다.

## 왜

WS 전환의 목적은 게이트·끼어들기·녹음·화자 판정을 서버가 쥐는 것이다. 게이트는 대기시간 동안 소리를 붙들어 짧은 대답을 버리고 응답을 늦췄다. 이제 대기시간은 "AI 말을 끊을지" 판정에만 쓴다.

## 곁가지 발견

기준선을 돌리다 게이트 업링크 버퍼가 통과 발화마다 늘었다(`buffered=18→33→47`, `dropped=1`). 게이트가 통과 발화를 4배속으로 내보내는 동안 라이브 프레임을 꺼내지 않는다. 그래서 발화 길이의 1/4 이 기반 지터버퍼에 쌓이고, 1배속 소비라 줄지 않는다. 운영 WebRTC 경로에도 있을 수 있어 dev 로그 확인 작업으로 따로 떼었다.
