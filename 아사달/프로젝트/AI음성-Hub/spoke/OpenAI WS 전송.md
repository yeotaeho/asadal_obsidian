# OpenAI WS 전송

> [!summary] 한 줄 요약
> 서버↔OpenAI 구간을 WebRTC 대신 WebSocket 으로 붙이는 dev 실험이다. 1차(전송만)와 2차(서버가 턴을 쥠)가 dev 에 머지됐고 실통화에서 끼어들기 판정이 정상 동작했다. 일시정지·멈춤 보완은 dev PR 대기, 응답 요청 방식(서버 요청 +0.31초 vs 자동 응답 하이브리드)은 결정 대기다. 서비스: [[AI음성]]

## 무엇을 했나

| 단계 | 내용 | 상태 |
|---|---|---|
| 1차 | 플래그를 켠 세션만 WS 로 연결. 답변은 조각을 모아 실시간 박자로 내고, WebRTC 전용 버퍼 이벤트는 우리 재생 기준으로 만든다 | **dev 머지 (#67)** |
| 2차 | 턴 판정. 게이트 대신 원음을 보내고, 대기시간은 끼어들기 판정에만 쓴다. OpenAI 자동 끼어들기·자동 응답을 끄고 채널이 응답을 요청한다. 일시정지는 채널 트랙도 같이 멈추고, 멈춤·종료는 도구 답 대기까지 끝낸다 | **dev 머지 (#68)·실통화 정상**, 일시정지·멈춤 보완은 푸시(`c2c24c9`) |
| 3차 | 화자 판정 연결. 말 2초 시점에 계산해 끼어들기 판정 입력으로 쓴다 | 2차 dev 확인 뒤 |
| 4차 | 녹음·종료말을 WS 방식으로 정리 | 3차 뒤 |
| 5차 | 전환. dev 기본값 → 운영 봇 단위 → 운영 기본값 → OpenAI 쪽 WebRTC 경로 제거 | 대역폭·법무 확인 뒤 |

브라우저↔서버 구간과 프론트는 바꾸지 않는다. 브라우저가 보내는 OpenAI 제어 메시지(truncate·response.create)는 서버가 버린다.

## 무엇이 달라졌나

**1차** — dev 비교에서 첫 답변 소리까지 WS 는 중앙값 779ms(5회), WebRTC 는 504ms(6회)였다. OpenAI 가 WS 로 답변 소리를 400ms 조각으로 보내는 탓이다. 대신 WS 다운링크는 dropped·underflow 가 0 이었고, WebRTC 통화는 OpenAI 구간 RTP 손실이 3.3% 였다.

**2차** — 재현 시험(대기시간 1.2초, 합성음)에서 조용할 때 "네"(0.7초)에 답했다. 기준선은 게이트가 버려 무응답이었다. AI 말 중 질문은 입력 **2.4초 → 1.7초** 뒤에 끊겼다. 기침과 "네"는 두 방식 모두 끊지 않았다.

대가도 쟀다. 서버가 응답을 요청하면 커밋부터 `response.created` 까지 턴마다 중앙값 **0.31초**가 더 걸렸다(9회). 자동 응답은 0초다.

```
AI 조용  : 말 시작 → 바로 알림 → 말 끝(committed) → 말소리 비율 통과면 response.create
AI 차례  : 말 시작 → 붙듦 ─┬ 대기시간 동안 3관문 통과 → 취소·버림·자르기 → 말 시작 알림 → 끝나면 응답 요청
                           └ 그 전에 끝남 → 항목 삭제, 전사 숨김(AI 는 계속 말함)
미사용 봇: 말 시작 → 즉시 끊고 알림
```

## 왜

화자 판정으로 실제로 거르려면 응답별 소리와 턴을 서버가 쥐어야 한다. WS 는 답변 조각마다 `response_id`·`item_id` 가 붙고 재생 시점을 서버가 정한다. 사용자 목표는 게이트·끼어들기·녹음·화자 판정을 WS 위로 옮겨 정확성과 확장성을 얻는 것이다.
