# 음성채팅 종료 안내말

> [!summary] 한 줄 요약
> 종료 버튼을 누르면 관리자가 설정한 종료 안내말을 AI가 말하고 나서 세션을 닫는 기능. 백엔드는 main 에 들어갔고, **2026-09-18 종료말 간헐 누락 결함을 `fix/voice-end-farewell` 에서 수정(dev 확인 전)**. 서비스: [[AI음성]] · 대칭 기능: [[음성채팅 첫 인사말]]

## 무엇을 했나

[[음성채팅 첫 인사말]] 과 같은 구조로 반대편(종료)을 배선했다. 프론트는 이미 `voice_end_msg` 를 저장 payload 에 담아 보내고 있었지만 본체가 받아주지 않아 값이 버려지고 있었다.

| 구간 | 내용 |
|---|---|
| 본체 (Chatty_Project) | `voice_end_msg` 필드 수용 — 요청 모델 + SQLite 컬럼 + 조회 SELECT (4줄) |
| AI_Pro_VOICE | 로더가 인사말·종료말을 한 번에 읽고, `voice_end.request` 를 받으면 응답 큐로 발화 후 `voice_end.done` 통지 |
| 프론트 | 종료 버튼이 즉시 닫는 대신 이벤트를 주고받도록 순서 변경 |

## 프론트와의 계약

```
브라우저 → 서버 : voice_end.request   (종료 버튼, DataChannel)
서버 → 브라우저 : voice_end.message   (말풍선용 텍스트)
서버 → 브라우저 : voice_end.done      (발화 끝 — 이제 release 호출)
```

프론트는 `voice_end.done` 을 받은 뒤 release·PeerConnection close 를 호출한다. **안전 타임아웃(5~7초)을 반드시 둘 것** — OpenAI 가 응답하지 않는 경로는 서버가 받아낼 수 없다.

## 종료 시퀀스 (2026-09-18 개정)

종료는 **입력부터 끊는다.** 출력만 끊고 입력을 살려 두면 대기·발화 중인 종료말을 들어온 소리가 지운다.

```
종료 클릭
 → 업링크 프록시 pause (게이트가 붙든 발화도 방출 안 함)
 → input_audio_buffer.clear
 → response.cancel(항상) + output_audio_buffer.clear + 큐 폐기     state=cancelling
 → 결과: 몰랐던 응답의 response.created(→ queued) 또는 response_cancel_not_active(→ 발행)
 → 발행 → speaking → draining → output_audio_buffer.stopped → 서버 버퍼 드레인 → voice_end.done
```

| 상태 | 뜻 |
|---|---|
| `cancelling` | 확인용 cancel 의 결과 대기. 발행 보류 |
| `queued` | 취소된 응답의 `response.done`·재생 `cleared` 대기. 이 사이 시작된 재생은 즉시 비움 |
| `speaking` | 발행됨. 발행 뒤 첫 `response.created` 가 종료말 id |
| `draining` | 생성 완료, 재생 완료(`stopped`) 대기 |

네 상태 모두에서 발화 감지(끼어들기)는 무시한다.

## 무엇이 달라졌나

저장은 본체 배포만으로 즉시 시작된다 — 프론트가 이미 보내고 있어서 필드를 받아주기만 하면 된다. 기존 봇 DB 는 `check_and_add_missing_columns` 가 조회·저장 때 자동 `ALTER TABLE` 하므로 **700여 계정 마이그레이션 작업이 없다**.

로더는 **컬럼을 명시하지 않고 `SELECT *`** 로 읽는다. 컬럼명을 지정하면 본체 배포 전 봇 DB 에서 쿼리 전체가 `OperationalError` 로 죽어 **저장된 인사말까지 기본값으로 떨어진다**.

2026-09-18 수정으로 **답변 중·발화 직후·에코 환경에서 종료말이 가끔 사라지던 세 경로가 막혔다.** 확인용 cancel 한 번의 왕복만큼 종료말이 늦어진다.

## 왜

"음성 채팅 종료 시(버튼 클릭 시) 자동으로 종료 안내말을 출력하고 종료하면 된다"는 요청(서창녕, 2026-08-31). 시작만 인사하고 끝은 뚝 끊기던 비대칭을 없앤다.

2026-09-18 수정은 "RAG·발화 중·끼어들기·답변 중 종료는 대부분 되는데 가끔 종료말이 안 나온다"는 사용자 보고에서 시작했다.

## 함정

가장 큰 함정은 **`response.done` 이 "생성 완료"지 "재생 완료"가 아니라는 것**이다. dev 실측으로 생성 완료 뒤에도 **오디오가 2.6초 더 남았다**. 재생 완료는 `output_audio_buffer.stopped` 가 알려준다.

- **생성 ≠ 재생** — 완료 판정은 `output_audio_buffer.stopped` 로 한다.
- **종료는 즉시 중단** — 하던 답변을 끝까지 듣게 하지 않는다. `response.cancel`(생성) + `output_audio_buffer.clear`(재생).
- **취소는 요청일 뿐이다** — 확인이 올 때까지 종료말은 대기한다. 이 창에 입력이 살아 있으면 종료말이 지워진다(2026-09-18).
- **서버가 모르는 자동 응답** — 발화 직후엔 OpenAI 가 응답을 만들었어도 `response.created` 전이라 `pending` 이 비어 있다. 그래서 항상 cancel 하고 결과를 본다. cancel 뒤 곧바로 발행하면 뒤늦은 `created` 가 종료말 id 로 오인된다.
- **게이트는 발화를 붙든다** — 프론트 마이크 off 만으로는 클릭 직전 말이 400ms 뒤 방출된다. 업링크 트랙을 서버에서 멈춘다.
- **뒤늦은 답변 폐기** — 종료 후 끝난 RAG·tool 작업이 답변을 큐에 넣는다. 큐 입구에서 버린다.
- **`response.id` 는 재생 완료까지 들고 있는다** — 지우면 남의 `stopped` 로 재생 도중 끊긴다.
- **완료 판정은 큐 펌프보다 먼저**.
- **발행 실패 = 영영 안 오는 `done`** — `pending` 미설정으로 판별해 바로 `voice_end.done`.
- **attach_track 전 구간** — 매니저가 쥔 채널을 넘겨서 해결.
- **제어 JSON 이 사용자 발화로 샌다** — 라우팅에서 걸러낸다.
- **확인용 cancel 의 에러** — `response_cancel_not_active` 는 정상 흐름이라 브라우저 중계에서 뺀다.

## 남은 위험

**cancel 처리 뒤에 생기는 자동 응답**은 막지 못한다. 업링크를 멈추기 전 이미 OpenAI 로 날아간 소리가 cancel 뒤에 커밋되는 경우다. 종료말이 거부되고 그 응답이 종료말로 오인된다. `input_audio_buffer.clear` 로 창을 좁혔고, 넘어오면 프론트 타임아웃이 받아낸다.

정확히 하려면 `response.create` 에 `metadata` 를 실어 대조해야 한다. 하지만 GA 모델에서 추가 필드가 `Unknown parameter` 로 깨진 전력이 있어 실서버 확인 없이는 넣지 않는다.
