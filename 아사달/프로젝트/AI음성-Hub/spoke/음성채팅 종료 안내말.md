# 음성채팅 종료 안내말

> [!summary] 한 줄 요약
> 마이크 버튼을 다시 눌러 통화를 끝낼 때 관리자가 설정한 종료 안내말을 AI가 말하고 나서 세션을 닫는 기능. **백엔드 양쪽 구현·리뷰 완료(푸시됨), 프론트 종료 시퀀스 연결이 남았다.** 서비스: [[AI음성]] · 대칭 기능: [[음성채팅 첫 인사말]]

## 무엇을 했나

[[음성채팅 첫 인사말]] 과 같은 구조로 반대편(종료)을 배선했다. 프론트는 이미 `voice_end_msg` 를 저장 payload 에 담아 보내고 있었지만 본체가 받아주지 않아 값이 버려지고 있었다.

| 구간 | 내용 |
|---|---|
| 본체 (Chatty_Project) | `voice_end_msg` 필드 수용 — 요청 모델 + SQLite 컬럼 + 조회 SELECT (4줄) |
| AI_Pro_VOICE | 로더가 인사말·종료말을 한 번에 읽고, `voice_end.request` 를 받으면 응답 큐로 발화 후 `voice_end.done` 통지 |
| 프론트 | **미착수** — 종료 버튼이 즉시 닫는 대신 이벤트를 주고받도록 순서 변경 필요 |

## 프론트와의 계약

```
브라우저 → 서버 : voice_end.request   (마이크 재클릭, DataChannel)
서버 → 브라우저 : voice_end.message   (말풍선용 텍스트)
서버 → 브라우저 : voice_end.done      (발화 끝 — 이제 release 호출)
```

프론트는 `voice_end.done` 을 받은 뒤 release·PeerConnection close 를 호출한다. **안전 타임아웃(5~7초)을 반드시 둘 것** — 서버가 응답 못 하는 경로가 남아 있다(아래 함정).

## 무엇이 달라졌나

저장은 본체 배포만으로 즉시 시작된다 — 프론트가 이미 보내고 있어서 필드를 받아주기만 하면 된다. 기존 봇 DB 는 `check_and_add_missing_columns` 가 조회·저장 때 자동 `ALTER TABLE` 하므로 **700여 계정 마이그레이션 작업이 없다**.

로더는 **컬럼을 명시하지 않고 `SELECT *`** 로 읽는다. 컬럼명을 지정하면 본체 배포 전 봇 DB 에서 쿼리 전체가 `OperationalError` 로 죽어 **저장된 인사말까지 기본값으로 떨어진다** — 배포 순서가 어긋나는 구간을 견디기 위한 선택이다.

## 왜

"음성 채팅 종료 시(버튼 클릭 시) 자동으로 종료 안내말을 출력하고 종료하면 된다"는 요청(서창녕, 2026-08-31). 시작만 인사하고 끝은 뚝 끊기던 비대칭을 없앤다.

## 어디

| 구분 | 내용 |

## 함정 (Codex 리뷰 4회전에서 확정)

가장 큰 함정은 **`response.done` 이 "생성 완료"지 "재생 완료"가 아니라는 것**이다. dev 실측으로 생성 완료 뒤에도 **오디오가 2.6초 더 남았다** — 그 시점에 끊으면 안내말이 문장 중간에서 잘린다. 재생 완료는 `output_audio_buffer.stopped` 가 알려준다.

- **생성 ≠ 재생** — 완료 판정은 `output_audio_buffer.stopped` 로 한다. 답변 도중 종료도 같은 원인이었다 — 재생이 남은 구간에 종료말을 발행하면 둘이 겹쳐 **양쪽 다 안 나온다**.
- **종료는 즉시 중단** — 하던 답변을 끝까지 듣게 하지 않는다. `response.cancel`(생성) + `output_audio_buffer.clear`(재생) 를 보낸 뒤 종료말을 낸다. 두 이벤트를 보내는 경로는 이 작업에서 새로 만들었다.
- **뒤늦은 답변 폐기** — 종료 후 끝난 RAG·tool 작업이 답변을 큐에 넣는다. 큐를 비우는 것만으로는 못 막으므로 큐 입구에서 버린다.
- **`response.id` 는 재생 완료까지 들고 있는다** — 생성 완료 시 상태와 함께 지우면 id 가드가 무력해져 남의 `stopped` 로 재생 도중 끊긴다.
- **완료 판정은 큐 펌프보다 먼저** — 펌프가 대기 중이던 종료말을 꺼내 `speaking` 으로 바꾸면, 방금 끝난 다른 응답을 종료말 완료로 오인한다.
- **발행 실패 = 영영 안 오는 `done`** — OpenAI 채널이 닫혀 있으면 `_issue_response_create` 가 조용히 반환한다. `pending` 미설정으로 판별해 바로 `voice_end.done` 을 보낸다.
- **끼어들기가 큐를 비운다** — 종료말도 그 큐에 있다. 상태만 남기면 재클릭이 "이미 진행 중"으로 걸러져 **버튼이 그 세션 내내 죽는다**.
- **attach_track 전 구간** — 브릿지의 채널 맵·메타데이터는 `attach_track` 이 채운다. 그전에 종료를 누르면 맵으로 채널을 못 찾아 아무 응답도 못 보낸다. 매니저가 쥔 채널을 넘겨서 해결.
- **v3 파사드는 메서드 3개만 위임** — `v3/` 는 바이트 고정이라 늘릴 수 없어 매니저가 `_impl` 을 직접 참조한다.
- **제어 JSON 이 사용자 발화로 샌다** — `_extract_text` 는 text/transcript/content 가 없으면 원문을 그대로 돌려준다. 라우팅에서 걸러내지 않으면 종료 요청 JSON 이 LLM 입력이 된다.

##### 기각된 가설 — 마이크 누수 끼어들기

스피커로 나가는 안내말이 마이크에 들어가 끼어들기로 판정된다고 두 번 추정했으나 **둘 다 틀렸다**. 취소 주체는 우리 코드가 아니라 GA 세션의 `interrupt_response: True`, 즉 OpenAI 내부다. 서버 가드로는 막을 수 없고, 막으려면 마이크를 꺼야 한다(프론트에서 처리). 실제 원인은 위의 생성/재생 타이밍이었다.

## 남은 위험 (의도적 미채택)

종료말 상관을 **순서 기반 추정**으로 둔다. OpenAI 자동 응답의 `response.created` 가 우리 발행 직후에 끼어들면 그 id 를 종료말로 오인할 수 있다. 정확히 하려면 `response.create` 에 `metadata` 를 실어 대조해야 하는데, 이 코드베이스는 **GA 모델에서 `response.create` 추가 필드가 `Unknown parameter` 로 깨진 전력**이 있어 실서버 확인 없이는 넣지 않기로 했다. 그 경우 응답이 이미 활성이라 우리 `response.create` 자체가 거부되므로 기다릴 종료말도 없고, 프론트 타임아웃이 받아낸다.
