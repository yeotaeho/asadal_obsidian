# AI음성

> [!summary] 한 줄 요약
> 실시간 음성 채팅(WebRTC + OpenAI Realtime)·STT/TTS·음성 학습·회의록 서비스. 롤백됐던 음성채팅 v4를 v3와 분리해 복원했고, 품질을 v3 동급으로 끌어올린 뒤 **모바일 실기기에서 v4 음성 대화가 동작하는 것까지 확인했다 — 과제 1번 목표 달성.** GA 즉답 경로 5커밋을 원본(main 기준) 브랜치에 이식해 main PR 준비가 끝났고, 프론트 정식 PR이 남았다.

## 서비스 개요

AI프로의 음성 기능 전반을 담당한다. 백엔드는 `Chatty_Project/ai_voice/`, 음성 프론트엔드는 이 레포가 아니라 Gitea `Ji-Hwan/frontend`의 `chat/voice/`에 있다.

음성채팅은 v1~v4 버전이 있고 운영은 v3(브릿지리스, 브라우저↔OpenAI 직결)다. 구조 상세는 [[v3와 v4 아키텍처]] 참고.

## 무엇이 달라졌나

**Realtime 모델이 `gpt-realtime-2.1` 로 올라갔고, 모델 버전을 올려도 안 깨지는 구조가 됐다.** 기존에는 GA 여부를 고정 집합 `{gpt-realtime-2, gpt-realtime-2.0}` 으로 판정해서, 2.1 을 넣으면 집합에 없다는 이유로 **2026-05-12 에 폐지된 Legacy 경로로 조용히 떨어졌다**. 프론트는 같은 모델을 `startsWith('gpt-realtime-2')` 로 GA 라고 판정하므로 프론트만 정상이라 믿는 어긋난 상태가 된다. 판정을 프론트와 같은 접두사 규칙으로 통일해 다음 버전(2.2)에서도 같은 사고가 나지 않는다. 전환 전에 2.1 이 현재 v4 GA 세션 설정을 그대로 받는지 OpenAI 에 직접 물어 **대조군과 함께 HTTP 201** 을 확인했다. 경위는 [[AI음성 - Realtime 모델 2.1 전환과 GA 판정 통일]] 참고.

**복원 완전성이 오리지널 최종본 기준으로 검증됐다.** `origin/backup/voice-v4`(tip `318c0db`)와 파일·함수·인스턴스 속성 단위로 전수 대조해, 오리지널 마지막 운영 수정(PR #585)에서 유실된 2건 — 브라우저 제어 JSON의 runtime 전달 차단(RAG 이중 실행·메모리 누수 방지), 사용자 텍스트 FIFO 직렬화 — 을 찾아 재이식했다. Codex 리뷰 4라운드에서 워커 수명주기 경합 2건(잔여 항목 방치, 재접속 시 이전 워커의 늦은 정리)을 추가로 보강했다. 나머지 오리지널 기능(토큰 사용량 반환, 이벤트 중계, 필터 1초 완화, 좀비 스위퍼 등)은 모두 복원돼 있음을 확인했다. 경위는 [[AI음성 - backup 전수 대조와 유실 수정 재이식]] 참고.

**v4 응답 시작 경로가 오리지널과 같아졌다.** 복원 과정에서 GA 모델 LangGraph 스킵 가드(`e12eeea`)가 유실돼, 이중 응답을 자동 응답 차단(create_response=False)으로 누르면서 느린 서버 경로 — 전사 대기 + 턴 버퍼 1.5초 + Decision LLM + RAG 중복 — 만 남아 있었다. 오리지널 방향(자동 응답 복원 + v4 GA 세션 한정 LangGraph 스킵)으로 되돌렸고, Codex 리뷰에서 나온 경합 3건(자동 응답 pending 미표시, 끼어들기 판정 누락, 진행 중 tool 태스크 잔존)도 함께 잡았다. 실기 응답 속도 재측정은 dev 배포 후다.

**모바일에서 v4 음성 대화가 처음으로 동작한다** — 폰(안드로이드) 실기기 확인. 원인은 프론트가 ICE 후보 수집을 기다리지 않고 후보 0개 오퍼를 보내던 것이었고, 수집 대기 패치 하나로 해결됐다. 이 건으로 서버 코드는 무변경이다 — 서버는 표준대로 동작하고 있었다.

**v4 음성 품질이 v3 동급으로 올라왔다.** 업링크 게이트·지터버퍼를 걷어낸 재설계 후 dev 실측 — 발화 소실 **2/3건 → 0건**, 감지 지연 **+3.5초 → +0.3~0.5초**, 소음 오반응 0 유지. 잔여 격차는 이중 트랜스코딩의 +0.1~0.3초뿐이다.

**데스크톱 v4는 끝까지 동작한다.** 발화당 응답 하나, RAG 반영, 에러 토스트 없음 — 실기 확인. **모바일은 서버 코드 무죄가 확정됐다.** 폰의 UDP가 서버에 도달하지 않는 네트워크 문제(ICE checking 정지)로 좁혀졌고, 방화벽 소스 제한 가설로 과장님 확인 대기 중이다.

**v4가 dev에서 실제로 동작한다.** aiortc 재현 클라이언트로 3단계에 걸쳐 실측했다.

| 단계 | DataChannel 이벤트 | 인바운드 오디오 |
|---|---|---|
| 수정 전 | 0건 | **0프레임** |
| GA 세션 설정 전달 후 | 3건 (`error` 포함) | 1,123프레임 |
| `session.update` 가드 후 | **2건** | 1,107프레임 |

오디오가 초당 약 47프레임으로 끊김 없이 들어오고, 매 통화마다 뜨던 에러 토스트도 사라졌다. 경위는 [[AI음성 - v4 무음 원인 규명]]과 [[AI음성 - v4 배포 검증과 GA session.update 가드]] 참고.

v4 세션 생성이 **약 10초 → 약 10ms**로 단축됐다 (ICE 수집 지연 제거, 2개 연결 지점).

v4가 **기본 활성**이라 배포하면 바로 `/AI_voice/voice-chat-v4/*` 경로가 열린다. 문제가 생기면 `ENABLE_VOICE_V4=off`로 코드 배포 없이 즉시 끌 수 있다.

v3 운영 경로는 **바이트 단위 무변경**이며 스모크 테스트가 이를 고정한다. 라우터뿐 아니라 `v3/` 서비스 패키지 전체가 대상이다. 실제로 트래픽이 v4로 가려면 프론트 배포본에도 v4 폴백이 들어가야 한다.

**v4 소스에 `voice_chat.v3` 참조가 하나도 없다.** 세션이 어느 경로로 만들어졌는지에 따라 `server_webrtc`가 v3/v4 orchestrator를 골라주고, v4는 `v4/` 아래 자기 사본만 쓴다. 이제 v4를 고치려고 v3를 건드릴 일이 없다.

세션 정리에 **generation** 개념이 들어갔다. 같은 `session_id`가 재사용될 때 이전 세대의 늦은 정리가 새 세션을 부수던 문제를 막는다. 재현해보니 리뷰가 지목한 "예약된 콜백이 늦게 실행됨"은 일어나지 않고, 실제 창은 `close()`가 **진행 도중** 새 세대를 가로지르는 것이었다 — 그래서 진입 검사만으로는 부족하고, `close()`가 첫 `await` 전에 자기 세대 자원을 전부 떼어내도록 구조를 바꿨다. 경위는 [[AI음성 - 세션 재사용 경합 수정]] 참고.

공용 자산은 제대로 재사용하고 있다. v4가 import하는 프로젝트 모듈 **13개 전부**가 `main`에 이미 있던 것이다 — RAG 검색·챗봇 ID 조회·프롬프트 정책·세션 스키마 검증·상수 6개. 모델명·타임아웃 하드코딩 **0건**, 새 환경변수 **2개**뿐이다. 감사에서 나온 유일한 재발명은 `v4/rtp_stats_utils.py` 423줄이었고 삭제했다. 경위는 [[AI음성 - 공용 자산 재사용 감사]] 참고.

## 프론트 현황 (2026-08-13 실사)

로컬 미러(`AI_pro/voice/js/`)를 직접 읽어 확인했다. 미러는 git 저장소가 아니라 커밋 이력이 없다.

**ICE 수집 대기 패치는 반영돼 있다.** `webrtc_voice_module.js:307-333` — `setLocalDescription` 후 `icegatheringstatechange`로 수집 완료를 기다렸다가(폴백 상한 **2초** 하드코딩) 후보가 포함된 `pc.localDescription.sdp`를 POST한다. STUN은 구글 단일, TURN 없음.

**GA 마이그레이션은 2026-08-13 에 2.1 전환까지 끝났다.** 아래는 수정 후 상태다.

| 항목 | 상태 |
|---|---|
| 기본 모델 | **`gpt-realtime-2.1`** — `voice_runtime.js:3` |
| dialect 분기 | `gpt-realtime-2*` → ga, 그 외 legacy — `:189-196` (백엔드와 같은 접두사 규칙) |
| session.update | GA면 전송 생략 (flat 포맷 거부 대응) — `:1440-1445` |
| GA 런타임 에러 | **자동 폴백 제거** — 오류를 그대로 보고 |
| 모델 정규화 | `gpt-realtime` → **`gpt-realtime-2.1`** (3파일 동시 수정) |
| 이벤트 타입 | GA/legacy 양쪽 이름 모두 처리 (브리지 포함) |

`node --check` 4파일 통과. **아직 업로드 전이다** — 파일질라로 올려야 반영된다.

프론트에는 OpenAI 직접 호출이 없어서 (SDP는 전부 자체 백엔드 경유) 제거할 베타 헤더 자체가 없다 — 베타 헤더는 백엔드 관심사(`ai_voice/constants.py`).

잔여 이슈 2건.

- `webrtc_voice_widget.js:100` — 구형 독립 위젯에 `gpt-4o-realtime-preview-2024-12-17`(2026-05-07 폐지) 하드코딩. **미러 안에 참조가 없어** 사용 여부 불확실. 안 쓰이면 삭제, 쓰이면 이미 깨져 있다
- `?v=` 캐시 파라미터 전무 — 동적 로드부(`voice_webrtc_handler.js:330`)에도 없어 **파일을 고쳐도 브라우저 캐시로 구버전이 실행될 수 있다.** 이번 업로드에도 그대로 해당된다

모델 정규화가 **3파일에 중복**돼 있는 구조는 그대로다(`webrtc_voice_module.js`, `voice_input_plugin.js`, `modes/voice_webrtc_handler.js`). 다음 모델 변경 때도 3곳을 함께 고쳐야 한다.

## 왜

담당 과제 1번(AI음성 모바일 오류 수정)의 실체가 "v3 버그 수정"이 아니라 **롤백된 v4를 모바일에서 동작하게 부활**시키는 것이었다.

조사 결과 모바일 ICE/NAT(TURN 부재) 가설은 4G 실기기 테스트로 기각됐고, 진짜 병목은 서버 aiortc의 **ICE 수집 5초 고정 지연**(요청 처리 프로세스가 그동안 통째로 묶임 → 버튼 무반응)으로 실측 확인됐다. 과거 롤백의 재발을 막기 위해 v3 불가침·성공 경로 warning 금지를 전역 제약으로 강제하며 복원했다. 경위는 [[v4 복원 작업 현황]], [[운영에서만 터지는 문제들]] 참고.

그런데 복원 후 재검토에서 그 제약이 실제로는 지켜지지 않고 있었다는 게 드러났다. v4 라우터가 자체 orchestrator를 갖고도 공용 `server_webrtc`를 거쳐 v3 것을 타고 있어서, v4의 RAG 결함을 고치려면 v3 파일을 고쳐야 했다. 2026-07-13 롤백과 같은 실수가 한 층 아래에서 반복된 셈이라 세션별 분기로 정리했다.

> [!warning] 실행 구조 정정 (2026-08-13 서버 실측)
> 여러 노트가 "gunicorn 워커 4개"를 전제로 쓰여 있었는데 **근거가 없는 숫자**였다.
>
> | 항목 | 실제 |
> |---|---|
> | dev Chat App(9010) | **uvicorn 단독 실행** (`kss_app.service`). 워커 개념 없음, 프로세스 1개 |
> | 이 서버의 다른 gunicorn | 전부 **`--workers 2`** (명령줄 지정) |
> | 운영 Chat App 워커 수 | **미확인** |
> | `APP_WORKERS = 4` | `config.example.py` 기본값일 뿐 구동에 안 쓰임 |
>
> `gunicorn.conf.py` 는 `worker = ...` 로 **단수**라 gunicorn 이 인식하지 못한다(설정 이름은 `workers`). 지금은 명령줄 인자가 우선해 무해하지만 그 인자를 빼면 워커 1개가 된다 — **그대로 두기로 결정.**
>
> 실무상 함의 두 가지. **①** 이벤트 루프 불일치 수정(`_get_loop`)은 dev 에서 재현·검증이 불가능하다 — 운영 배포가 첫 검증이다. **②** v4 동시성 부하 측정을 dev 에서 해도 운영에 그대로 적용할 수 없다. 상세는 [[gunicorn 멀티워커 구조]].

## 배포 검증 절차

dev 머지(`app restart`) 후 v4가 실제로 올라왔는지 확인한다.

```bash
curl -k https://dev.chatbaram.com:9000/openapi.json | grep -c "voice-chat-v4"
```

v4가 기본 활성이므로 **0보다 커야 정상**이다. 별도의 `ENABLE_VOICE_V4=on` 설정 단계는 필요 없다.
