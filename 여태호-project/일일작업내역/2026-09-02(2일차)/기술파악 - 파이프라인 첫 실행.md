# 파이프라인 첫 실행

> [!summary] 한 줄 요약
> 수집된 4,656건 위에서 파이프라인을 처음 돌렸다. 1차는 크래시, 고친 뒤 2·3차는 완주. 실행 데이터가 설계 결함 셋을 드러내 7커밋으로 고쳤고 Codex 리뷰 6회를 거쳤다. 기능: [[MVP 파이프라인]]

## 무슨 작업

사용자가 "파이프라인 한 번 돌려보고 단계마다 검증해 달라"고 했다. `scripts/run_job.py pipeline` 을 세 번 돌렸다.

| 실행 | 결과 |
|---|---|
| 1차 | 첫 LLM 도달 항목에서 `MissingGreenlet` 크래시. 배치 중단 |
| 2차 (수정 후) | 50건 완주. 규칙 탈락 14, 규칙 통과 36, 점수 탈락 33, LLM 도달 3 |
| 3차 (우회 도입 후) | 50건 완주. LLM 도달 **14** (YouTube 5 + arXiv 9) |

LLM 키가 없어 관문 ⑤ 는 SDK `TypeError` 로 실패하고, 그 실패가 savepoint 롤백으로 `NEW`·`score=None`·`decisions 0` 으로 깨끗이 돌아오는 것까지 확인했다. 현재 DB: `NEW 4,578 / DROPPED 53 / FILTERED_OUT 25`, `decisions` 131행.

## 실행이 드러낸 결함 셋

### 1. savepoint 롤백 뒤 만료된 객체 접근 — `e9553ca`

LLM 실패 → `savepoint.rollback()` → `log.warning(item_id=item.id)`. 롤백이 `item` 을 만료시켜 `item.id` 가 동기 로드를 시도하고 `MissingGreenlet`. 3차 Codex 리뷰가 "안전해 보인다"고 했던 바로 그 지점이다.

실증 테스트: 중첩 롤백은 **savepoint 안에서 수정된 객체만** 만료시킨다(수정한 s1 은 10개 속성 만료, 손 안 댄 s2 는 정상). 그래서 `item_id` 를 진입 전에 빼는 것으로 충분했고, `collect.py` 의 `source` 는 손대지 않았다.

### 2. 화이트리스트가 점수 관문을 절대 못 넘음 — `64dda81` · `52bacbb` · `69436c4`

2차 실행에서 YouTube 5건이 전부 **0.25** 로 탈락했다. `always_pass_source` 경로가 키워드 매칭을 건너뛰고 `matched=[]` 로 반환해 kw=0. 신뢰도 1.0 도 최대 0.35 < 0.45.

```
YouTube  trust .6  kw 0  → 0.15 + 0    + 0.1 = 0.25  탈락
GitHub   trust 1.0 kw 0  → 0.25 + 0    + 0.1 = 0.35  탈락   ← 화이트리스트 전멸
arXiv    trust .5  kw 3  → 0.125 + 0.25 + 0.1 = 0.475 통과
```

모집단 재계산: GitHub 200건 중 점수 통과 **0 → 96**(키워드 반환 수정), YouTube 28건 중 27건이 키워드 0개라 여전히 **0**. 한국어 제목이 영문 키워드에 안 걸린다. 사용자 결정으로 `always_pass_source` 는 점수 관문을 **우회**하고 LLM 이 거른다.

우회를 넣자 Codex 가 첫 실행 백필(릴리즈 200·영상 30 = 230건)이 LLM 예산 300 을 잠식한다고 지적했다. 우회 소스 목록 분리 대신 **48h 신선도 가드**(`whitelist_max_age_hours`)를 택했다 — 관심 저장소 릴리즈도 LLM 판정을 받는 게 맞고, 문제는 오래된 항목뿐이다. 검증: 1.7년 전 릴리즈 → `whitelist_stale`, 2시간 전 영상 → `whitelist_bypass`.

### 3. dedupe 가 알림된 적 없는 항목을 기준으로 삼음 — `8291f30` · `f5b0298` · `707f432`

결정이 세 번 뒤집혔다.

| 단계 | 기준에서 제외 | 뒤집힌 이유 |
|---|---|---|
| 원래 | 없음 | 점수 탈락한 arXiv 논문이 하루 뒤 HN 에 떠도 dup 으로 죽음 |
| `8291f30` | DROPPED·FILTERED_OUT | FAILED(발송 3회 실패)도 사용자가 못 받은 알림 |
| `f5b0298` | + FAILED, **NEW 는 유지** | "NEW 대표가 mention_count boost 를 받는다"는 근거 |
| `707f432` | + **NEW** | 반례: 규칙에서 떨어질 A(NEW) 가 자기 힘으로 통과할 B 를 먼저 죽인다. boost 는 규칙 단계에선 무의미 |

최종: dedupe 기준은 **SCORED·QUEUED·SENT 뿐**이고, 다중 소스 신호는 `cluster_id` 연결 대신 `mention_count` 가 **점수화 시점에 유사 제목의 다른 소스 수를 직접 센다.** 처리 순서·상태와 무관하다. 먼저 SCORED 되는 쪽이 이후 상대의 기준이 되므로 둘 다 알림되진 않는다. 검증(롤백): A NEW → 기준 아님·multi 2, 같은 소스 → multi 1, A SCORED → 기준.

## 정정

앞선 노트에 "arXiv 대부분이 LLM 까지 가서 상한을 잠식한다"고 썼는데 **틀렸다.** 실측은 키워드 3개 이상만 통과해 **61/609 = 10%**, 하루 60건이다. `trust_score` 0.3 은 0.425 < 0.45 라 **0건**이 되는 이진 선택이지 미세 조정이 아니었다. 사용자 결정으로 0.5 유지.

```

DB 롤백 스크립트 3종   신선도 가드 · dedupe 기준 · mention_count — 전부 예상값, DB 불변
```

리뷰 마지막 라운드는 결함 없음. 후속으로 남긴 것: `mention_count` trigram 비용(데이터 커지면 `EXPLAIN ANALYZE`), 다중 워커 시 A·B 동시 SCORED 경합.

## 배운 것

순수 함수 테스트 56개가 전부 통과해도 "화이트리스트가 점수 관문을 절대 못 넘는다"는 건 보이지 않았다. **실제 데이터로 한 배치를 돌리고 `decisions` 를 읽는 것**이 가장 싼 설계 검증이었다. 그리고 리뷰어의 일반론("NEW 도 알림된 적 없다")은 기각했지만, 구체적 시퀀스를 요구하자 진짜 반례가 나왔다 — 기각할 때는 반례를 요구하는 게 맞다.
