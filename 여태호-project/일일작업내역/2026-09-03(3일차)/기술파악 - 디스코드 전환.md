# 디스코드 전환

> [!summary] 한 줄 요약
> 발송 채널을 텔레그램에서 디스코드 봇으로 바꿨다. 어댑터·인터랙션 엔드포인트를 만들고 Codex 리뷰 5회로 rate limit·이스케이프·URL 검증을 다듬었다. 키는 유효하지만 봇 초대와 채널 ID 교정이 남아 실제 발송은 아직이다. 기능: [[MVP 파이프라인]]

## 무슨 작업

사용자가 "디스코드로 할 것" 을 결정했다. 웹훅 URL 하나로도 보낼 수는 있지만 웹훅 메시지에는 버튼을 달 수 없어 피드백(👍/👎)이 빠지므로 **봇 방식**을 택했다. 발급 가이드를 쓰고 `.env`·`.env.example` 에 키 3개를 추가했다.

사용자가 키를 채운 뒤 구현했다. `Notifier` 프로토콜 덕에 어댑터 하나(`notify/discord.py`)와 라우터 하나(`api/discord.py`)를 붙이고 발송 잡의 기본값만 바꿨다. 텔레그램은 대안 어댑터로 남겼다. 소스 파일 **34개**, 테스트 **73개**.

## 키 검증에서 나온 것

읽기 전용으로 토큰·채널을 확인했다.

| 확인 | 결과 |
|---|---|
| `GET /users/@me` | **200** — 봇 `trend`, ID `1544729240434647182` |
| `GET /channels/{id}` | **404 Unknown Channel** |
| `GET /users/@me/guilds` | **`[]`** — 어느 서버에도 미초대 |

채널 ID 로 넣은 값이 봇 토큰 첫 세그먼트를 base64 디코드한 값과 같았다 — 즉 **Application ID 를 채널 ID 자리에** 넣은 것이다. 초대 URL(`permissions=19456`)과 채널 ID 잡는 법(개발자 모드 → 채널 우클릭)을 안내했다. 채널이 잡히면 테스트 발송 1건은 사용자 허락 후에 한다.

## 리뷰가 잡은 것 — 5회, Important 11건

| 라운드 | 지적 | 조치 |
|---|---|---|
| 1 | 429 의 `retry_after` 무시·4xx 3회 재시도 / 마크다운 이스케이프에 `[]()#>-` 누락 / 링크 버튼 URL 스킴 미검증 | 명시 재시도 루프, 이스케이프 확장, **`store_items` 에서 http(s) 아니면 적재 거부**(모든 수집 경로 공통) + 버튼은 스킴·512자 통과 시만 |
| 2 | `retry_after` 를 30초로 잘라 조기 재시도 / Discord 형식 `User-Agent` 없음 | 상한 초과는 재시도 없이 실패, `DiscordBot (url, version)` UA |
| 3 | 긴 429 뒤에도 같은 배치의 다음 항목·다음 잡이 바로 요청 | **프로세스 전역 게이트** `_blocked_until`. 게이트에 막히면 `RateLimited` → 발송 잡이 항목을 FAILED 로 기록하지 않고 배치 중단 |
| 4 | 동시 요청의 짧은 429 가 긴 게이트를 덮어써 줄임 / 짧은 429 3회 소진이 FAILED 로 기록 | `_extend_gate` 는 `max` 로 뒤로만, 매 시도 직전 재확인 / 소진도 `RateLimited` |
| 5 | 옛 기대값 테스트 잔존 | 중복 테스트 제거. 그 외 **결함 없음** |

핵심 통찰은 3라운드에 있다. `retry_after` 는 "이 요청의 재시도" 가 아니라 **"다음 요청까지의 대기"** 다. 실패로 기록만 하고 다음 항목을 보내면 디스코드 입장에선 제한 만료 전 요청이다. 그래서 "요청을 멈추는 것" 과 "항목 실패" 를 분리했다 — `RateLimited` 는 채널 공통 예외로 `base.py` 에 두고, 발송 잡은 이걸 받으면 `break` 한다.

## 테스트에서 배운 것

429 재시도 테스트에서 `asyncio.sleep` 을 즉시 반환시키는 픽스처를 썼더니 게이트(같은 길이)가 만료되기 전에 재시도해 `RateLimited` 가 났다. 실제 코드는 `sleep(wait)` 과 게이트가 같은 길이라 정상이다. `retry_after` 를 0.01초로 두고 실제 sleep 을 쓰도록 고쳤고, 함정으로 레퍼런스에 남겼다.
