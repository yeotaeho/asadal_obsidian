# 소스 확장 1차 설계·구현·리뷰

> [!summary] 한 줄 요약
> 소스 후보를 실측해 설계서·구현서를 쓰고, 서브에이전트 방식으로 Task 6개를 구현·리뷰한 뒤 전체 브랜치 리뷰 5라운드와 Codex 리뷰를 거쳐 **PR #5** 를 열었다. 기능: [[소스 확장 1차]]

## 무슨 작업

옵시디언·설계 문서·코드로 컨텍스트를 잡고 후보 소스 12개를 curl 로 실측했다. X 는 유료 전환, Reddit 은 승인 티켓이라 보류하고 HN·HF Papers·RSS 4개를 1차로 골랐다. 코드에서 병목 셋을 찾았다. 같은 URL 이 다른 소스에서 오면 `ON CONFLICT DO NOTHING` 으로 버려져 `hot`·`multi` 항이 사실상 0, 보강이 사설 IP 를 막지 않음, 첫 폴링이 피드 전체를 임베딩함.

설계서(`소스확장-1차-설계서.md`)와 구현서(`소스확장-1차-구현서.md`)를 승인받고 서브에이전트 방식으로 실행했다. Task 마다 구현 서브에이전트 1 + 리뷰 서브에이전트 1. Task 3 은 리뷰에서 `SKIP LOCKED` 지적을 받아 수정 후 재리뷰 통과.

전체 브랜치 리뷰가 Important 둘을 냈다. arXiv 교차 등재가 multi 를 만든다는 것과, HN 점수가 매 폴링 오르니 "값이 바뀌면 되살림" 이 무한 churn 이라는 것. 되살림 게이트는 세 번 고쳤다.

```
값이 바뀌면            → HN 10분 폴링마다 되살림·재탈락 (decisions 3~6k행/일)
근접 구간(임계값−0.10) → 고득점 항목은 구간 안에서 여전히 churn, 큰 단일 상승(블로그→HN 400점)은 차단
직전 관측 대비 변화량   → churn 은 멈추나 누적이 안 됨 (30→500점을 6번에 나눠 오르면 한 번도 안 넘김)
마지막 결정 breakdown 기준 → hot·multi 절대값 차이라 누적됨. multi 0 하한, fresh 감쇠분 반영
```

dev 브랜치에서 `sync collect pipeline` 을 돌려 HN **30/30**, HF **50/46** (arXiv 4건 병합), 배치 scored 3·4 를 확인했다. family 적용 뒤 arXiv 커서를 초기화해 재폴링하니 교차 등재 멘션 **0건**.

## 왜

사용자가 소스 확장을 요청했다. 허브의 "HN·Reddit·Trending·X 미착수" 항목이었고, v2 이후 예산(선별 60회·판정 300회·Voyage RPM 3)을 지키려면 커뮤니티가 이미 고른 것만 받아야 했다. 서브에이전트 방식은 사용자 선택.
