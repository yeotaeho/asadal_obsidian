# 기술파악 - 결정 기록

> [!summary] 한 줄 요약
> 확정된 설계·운영 결정과 **기각한 대안**. 같은 조사를 두 번 하지 않기 위한 문서다. 서비스: [[기술파악]]

## 아키텍처 (구현도 2.2절)

| 결정 | 채택 | 기각한 대안 | 이유 |
|---|---|---|---|
| 큐 | **Postgres `status` + `FOR UPDATE SKIP LOCKED`** | Redis / Celery / RQ | 단일 사용자·소량 트래픽. 인프라가 하나 줄고 상태 조회·디버깅이 SQL 한 줄 |
| 스케줄러 | **APScheduler (AsyncIOScheduler)** | cron / Temporal | 소스별 5분~6시간 주기를 코드로 관리. 프로세스 내 실행이라 배포가 단순 |
| DB | **Neon (서버리스 Postgres)** | VM 위 자체 Postgres 컨테이너 | 운영·백업 부담 없음, 브랜치로 dev/운영 분리, `pg_trgm` 지원 |
| 중복 제거 | **제목 유사도 (pg_trgm)** | 임베딩 유사도 | 대부분의 중복은 같은 URL 또는 거의 같은 제목. 임베딩은 4단계에서 재검토 |
| 크롤링 | **trafilatura (보강 단계만)** | WaterCrawl / Crawl4AI | MVP 보류. JS 렌더링이 필요해지면 `sources/` 플러그인으로 검토 |
| 푸시 채널 | **텔레그램 봇 선행 → 앱 확장 (C안)** | 앱 + FCM 직행(A) / 봇만(B) | 핵심 가치는 수집·필터 파이프라인. 먼저 검증하고 앱은 3단계 |
| 본문 보강 시점 | **점수 통과 후, LLM 직전** | 수집 시점 | 탈락할 항목의 원문 페이지까지 긁지 않기 위해 |
| 패키지 구조 | **파이프라인 단계별 레이어드** | 헥사고날(`domain`/`application`/`adapters`) | 지금 규모에 층을 더 나눌 이유가 없음. 순수 함수는 이미 DB 없이 테스트됨 |

## 구현 단계에서 추가로 결정한 것 (2026-08-30)

| 결정 | 채택 | 기각한 대안 | 이유 |
|---|---|---|---|
| 텔레그램 클라이언트 | **httpx 직접 호출** | python-telegram-bot 21.x (구현도 3장에 적혀 있던 것) | 실제로 쓰는 API 가 `sendMessage`·`answerCallbackQuery` 둘뿐. 의존성 하나를 줄였다 |
| APScheduler jobstore | **MemoryJobStore (기본)** | Postgres jobstore (구현도 3장) | interval 잡을 기동 시 매번 재등록하므로 저장할 상태가 없다. 동적 잡 추가가 생기면 그때 |
| `user_prefs` 테이블 | **`config/rules.yaml`** | 테이블 생성 | 구현도 4장이 "MVP 는 YAML 로 대체 가능"이라 명시 |
| `Notifier.send` 시그니처 | **`(item, summary, level, source_name)`** | `(item, summary, level)` + ORM 관계로 소스 조회 | 메시지의 "출처: …" 줄에 이름이 필요한데 async 지연 로딩은 함정이 많다 |
| 클러스터 저장 | **`items.cluster_id` 컬럼** | 별도 `clusters` 테이블 | 대표 항목의 id 를 그대로 클러스터 키로 쓰면 테이블이 하나 준다 |
| MVP 소스 | **RSS · GitHub Releases · YouTube** | HN·Reddit·Trending·X 동시 착수 | 구현도 8장이 2단계로 배치. 소스 하나 = 파일 하나라 나중에 붙이는 비용이 낮다 |
| Discord notifier | **만들지 않음** | 어댑터 동시 구현 | 구현도 10장이 "처음 2주는 하나만" 권장 |
| LLM 구조화 출력 | **`messages.parse(output_format=...)`** | tool use 강제 호출 | 현재 SDK 의 권장 경로. Pydantic 모델을 그대로 넘기고 검증된 객체를 받는다 |
| LLM 모델 | **`claude-haiku-4-5`** (날짜 접미사 없음) | 상위 모델 | 구현도 3장이 저비용 Haiku 급으로 시작하도록 지정. 정확도 문제가 보이면 importance≥4 만 2단 판단 |

## 리뷰에서 나왔지만 반영하지 않은 것

| 지적 | 판단 | 이유 |
|---|---|---|
| `notifications(item_id, channel)` 유니크 제약 | **기각** | 중복 *발송* 자체를 막지 못하고 중복 *기록*만 막는다. 실제 피해(중복 텔레그램 메시지)는 그대로 두면서 잡만 죽인다. 발송을 예약-후-전송(outbox)으로 바꿀 때 함께 도입하는 게 맞다 |
| GitHub repo 별 커서 도입 | **보류** | 지금은 첫 페이지 20건만 본다. 폴링이 끊긴 사이 한 저장소에서 20개를 넘는 릴리즈가 나와야 누락이 생기는데, 관심 저장소 10개·30분 주기에서는 사실상 안 일어난다. 실제로 놓치면 그때 도입 (`github_release.py` 에 `ponytail:` 주석으로 표시) |

## 운영 파라미터 (초기값)

| 값 | 초기값 | 어디 |
|---|---|---|
| 점수 임계값 | **0.45** | `rules.yaml` `scoring.threshold` |
| 가중치 | src .25 / kw .25 / hot .2 / multi .2 / fresh .1 | `rules.yaml` `scoring` |
| 중복 판정 | 72시간 · similarity **0.6** | `pipeline/dedupe.py` (상수) |
| 하루 push 상한 | **15건** | `rules.yaml` `notify.daily_push_cap` |
| 무음 시간 | **23:00~08:00 KST** | `rules.yaml` `notify.quiet_*` |
| LLM 하루 상한 | **300건** | `.env` `LLM_DAILY_CAP` |
| 본문 보강 기준 | body **300자** 미만 | `pipeline/llm.py` (상수) |
| 파이프라인 배치 | 50건 / 120초 | `jobs/pipeline.py`, `jobs/scheduler.py` |
| 발송 배치 | 20건 / 180초 | `jobs/notify.py`, `jobs/scheduler.py` |

임계값·가중치는 `decisions` 로그를 보고 조정한다. 조정하면 이 표를 갱신하고 경위는 일일 노트에 남긴다.

## 미결

1. **Neon 무료 티어 컴퓨트 한도** — 유휴 시 자동 중지되므로 짧은 주기 폴링이 컴퓨트 시간을 계속 쓴다. 실제 사용량을 보고 야간 폴링 주기를 늘릴지 결정.
2. **3단계 앱 프레임워크** — Flutter vs Expo. 3단계 진입 시 결정.
3. **`rules.yaml` 핫리로드** — `reload_configs()` 는 있으나 호출부가 없다. 튜닝이 잦아지면 붙인다.
