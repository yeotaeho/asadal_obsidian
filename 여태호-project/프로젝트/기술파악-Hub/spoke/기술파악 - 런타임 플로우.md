# 기술파악 - 런타임 플로우

> [!summary] 한 줄 요약
> 프로세스가 뜨고 나서 항목 하나가 소스에서 텔레그램까지 가는 경로를, 예외 경로와 트랜잭션 경계까지 포함해 단계별로 적었다. 서비스: [[기술파악]]

## 기동

```
uvicorn app.main:app
  └ lifespan 진입
      ├ configure_logging()                     structlog JSON
      └ start_scheduler()                       SCHEDULER_ENABLED=true 일 때만
          ├ sync_sources()                      config/sources.yaml → sources 테이블
          │   ├ 이름이 같으면 갱신, 없으면 INSERT
          │   └ YAML 에서 빠진 소스는 enabled=false
          └ add_job × (활성 소스 수 + 2)
              ├ source:<이름>   interval = poll_interval_sec
              ├ pipeline        interval = 120초
              └ notify          interval = 180초
```

전부 `max_instances=1`, `coalesce=True` 다. 잡이 오래 걸려도 같은 잡이 겹쳐 돌지 않고, 밀린 실행은 한 번으로 합쳐진다.

## 1. 수집 — `run_source(source_id)`

```
session_scope() 열기                              ← 트랜잭션 시작
  Source 조회 → 비활성이면 0 반환
  build_source(cfg)                              레지스트리에서 타입별 인스턴스
  source.fetch(last_polled_at)                   ← 네트워크
  store_items()                                  ON CONFLICT (url_hash) DO NOTHING
  last_polled_at = now, last_error = None, fail_count = 0
커밋
```

**예외 경로** — `fetch()` 가 던지면 `fail_count += 1`, `last_error` 기록, `last_polled_at` **전진 안 함**(다음 폴링에서 같은 구간을 다시 본다). 연속 **5회**째면 실패 상태를 먼저 커밋한 뒤 텔레그램 운영 알림을 보낸다. 알림이 실패해도 로그만 남기고 실패 기록은 지켜진다.

**GitHub 만 예외** — `github_release` 는 `since` 를 무시하고 매번 최근 20건을 다시 본다. 저장소 하나가 실패해도 나머지는 수집되면서 `last_polled_at` 이 전진하기 때문에, 다시 보지 않으면 그 사이 릴리즈를 영구히 놓친다. 중복은 `url_hash` 유니크 제약이 막는다.

## 2. 웹훅 — 즉시 경로

```
POST /webhook/github
  HMAC-SHA256 검증 (X-Hub-Signature-256)         실패 → 401
  event != "release" 또는 action ∉ {published, released} → 무시
  release_to_item()                              폴링과 같은 변환 함수
  store_items()                                  → items(status=NEW)
```

여기서 끝난다. 이후는 스케줄러의 `run_pipeline` 이 이어받는다. **최대 2분** 뒤에 관문에 들어간다.

## 3. 관문 — `run_pipeline()`

```
session_scope() 열기
  budget = LLM_DAILY_CAP − 최근 24h summaries 수
  budget ≤ 0 → 즉시 0 반환                        ← 아무 항목도 건드리지 않는다
  _claim_batch()  50건, FOR UPDATE SKIP LOCKED, 최신순

  for 항목:
    budget ≤ 0 → break
    savepoint 시작                                ← 항목 하나 = savepoint 하나
      ① dedupe    72h 내 similarity > 0.6 → cluster_id 부여, FILTERED_OUT
      ② rules     exclude 우선 → always_pass → include_repo → include_keyword
                  탈락 → FILTERED_OUT
      ③ scoring   trust·kw·hot·multi·fresh 가중합, threshold 0.45
                  미달 → DROPPED
      ④ enrich    body < 300자면 원문 받아 trafilatura (타임아웃 10초, 실패해도 계속)
      ⑤ llm       messages.parse 1회 → summaries 저장
                  worth_notifying=false → DROPPED / true → SCORED
    savepoint 커밋
커밋
```

각 단계는 통과·탈락 여부를 `decisions` 에 남긴다. 이게 나중에 임계값을 조정할 유일한 근거다.

**예외 경로** — 항목 하나가 던지면 그 savepoint 만 롤백하고 다음 항목으로 간다. savepoint 가 없으면 rule·score 판정만 기록된 채 `NEW` 로 남아, 다음 실행에서 같은 판정이 `decisions` 에 또 쌓인다. LLM API 가 한 시간 죽어 있으면 **30회 × 50건 = 1,500행**이 쌓이던 경로였다.

**예산 소진** — `budget ≤ 0` 이면 항목을 claim 만 하고 처리하지 않는다. 판정을 기록해 두고 `NEW` 로 남기면 위와 같은 증식이 생기기 때문이다.

## 4. 발송 — `run_notify()`

```
session_scope() 열기
  visited = {}
  최대 20회 반복:
    _claim_one(visited)                          LIMIT 1, FOR UPDATE SKIP LOCKED
                                                 importance 내림차순 → published_at 오름차순
    없으면 break
    decide(importance, now)
      ├ importance ≤ 2          → level=None, reason=feed_only
      ├ 무음 시간(23~08 KST)의 push → level=None, reason=quiet_hours
      ├ 하루 상한(15) 초과       → level=SILENT, reason=daily_cap
      └ 그 외                    → level=PUSH 또는 SILENT

    level=None & feed_only  → notifications(level=feed) 기록, status=SENT
    level=None & 그 외       → status=QUEUED               (다음 실행에서 재시도)
    level 있음              → notifier.send() → notifications 기록, status=SENT
    커밋                                          ← 항목 하나 = 트랜잭션 하나
```

**왜 한 건씩 잠그나** — 20건을 한 번에 잠그고 루프 안에서 커밋하면 첫 커밋에서 나머지 19건의 `FOR UPDATE` 락까지 풀린다. 워커를 늘렸을 때 같은 항목이 두 번 발송될 수 있다.

**왜 `visited` 가 필요한가** — `QUEUED` 는 여전히 `PENDING` 조건에 걸린다. 제외하지 않으면 무음 시간에 같은 항목만 20번 다시 잡는다.

**예외 경로** — `send()` 가 실패하면(내부에서 이미 3회 재시도) `notifications` 에 error 를 남기고 `status=FAILED`. `FAILED` 는 `PENDING` 에 없으므로 자동 재시도하지 않는다.

## 5. 피드백

```
사용자가 👍/👎 탭
  → Telegram → POST /webhook/telegram
      X-Telegram-Bot-Api-Secret-Token 검증        실패 → 401
      callback_data "fb:useful:123" 파싱
      feedback INSERT + 커밋
      answerCallbackQuery (토스트)                실패해도 200 반환
```

토스트 실패로 500 을 돌려주면 텔레그램이 재전달해 피드백이 중복 기록된다. 그래서 예외를 삼킨다.

## 상태 전이

```
NEW ──dup/no_keyword──▶ FILTERED_OUT
NEW ──규칙 통과──▶ (점수) ──미달──▶ DROPPED
                        └─통과──▶ (LLM) ──false──▶ DROPPED
                                        └─true──▶ SCORED ──상한/무음──▶ QUEUED
                                                         └─발송──▶ SENT / FAILED
```

## 동시성

| 항목 | 지금 |
|---|---|
| 프로세스 | 1개 (FastAPI + APScheduler 같은 프로세스) |
| 잡 겹침 | `max_instances=1` 로 차단 |
| 큐 | Redis 없음. `items.status` + `FOR UPDATE SKIP LOCKED` |
| 커넥션 | 잡 하나 = 세션 하나, Neon pooled(pgbouncer), `statement_cache_size=0` |
| 워커 분리 시 | `SKIP LOCKED` 와 항목 단위 커밋 덕에 잡 수준에서는 안전. 다만 `decide()` 의 하루 상한 집계는 경합할 수 있다 |
