# 기술파악 - 런타임 플로우

> [!summary] 한 줄 요약
> 프로세스가 뜨고 나서 항목 하나가 소스에서 디스코드까지 가는 경로를 v2(임베딩·선별·탐색) 기준으로, 예외 경로와 트랜잭션 경계까지 단계별로 적었다. 수집·관문·발송은 Neon 에서 실전 확인됐고, 🧪 탐색 발송만 낮에 확인이 남았다. 서비스: [[기술파악]]

## 기동

```
uvicorn app.main:app
  └ lifespan 진입
      ├ configure_logging()                     structlog JSON
      └ start_scheduler()                       SCHEDULER_ENABLED=true 일 때만
          ├ sync_sources()                      config/sources.yaml → sources (trust_score 만, trust_adjusted 는 안 건드림)
          └ add_job × (활성 소스 수 + 2)
              ├ source:<이름>   interval = poll_interval_sec
              ├ pipeline        interval = 120초
              └ notify          interval = 180초
```

전부 `max_instances=1`, `coalesce=True`. 단일 프로세스가 전제다. `rules.yaml` 은 `extra="forbid"` 라 v1 키가 남아 있으면 여기서 죽는다.

## 1. 수집 — `run_source(source_id)`

```
session_scope() 열기
  Source 조회 → 비활성이면 0 반환
  try:
    source.fetch(last_polled_at)                 ← 네트워크
    savepoint
      store_items()                              http(s) 아닌 URL 거부 → ON CONFLICT DO NOTHING
    savepoint 커밋
  except: fail_count += 1, last_error, 5회째 운영 알림, 0 반환
  inserted 가 있으면 embed_pending(session, inserted)   ← Voyage 1회 (64건까지)
    실패 → NULL 로 두고 경고. 파이프라인 잡이 다시 시도
    EmbeddingDimError → 프로세스당 1회 운영 알림, source.last_error 에 남김 (적재는 유지)
  last_polled_at = now, fail_count = 0
커밋
```

임베딩 텍스트는 `제목 + 본문 300자`. 보강 뒤에도 다시 계산하지 않는다(같은 재료 원칙). 무료 등급 429 는 20초×시도 대기라 수집 잡이 최대 1분 길어질 수 있다.

## 2. 웹훅 — 즉시 경로

`POST /webhook/github` (HMAC) → `store_items` → NEW. 이후는 파이프라인 잡이 최대 2분 뒤에 받는다. 웹훅 경로는 임베딩을 계산하지 않는다 — 파이프라인 1국면 보충이 맡는다.

## 3. 관문 — `run_pipeline()` 3국면

```
session_scope() 열기
  _reembedding_in_progress? (embedding_model 이 설정과 다른 행 존재)  → 잡 종료 (백필 중)
  _claim_batch()  50건, FOR UPDATE SKIP LOCKED, 최신순   ← 잠금은 세 국면 내내 유지
  embed_pending(배치 id)                                 ← NULL 보충. 차원 오류면 알림 후 raise

  1국면 — 항목별 savepoint
    stale     published_at 이 72h 초과 → DROPPED(stale)          ← 선별 앞. 백로그가 예산을 못 씀
    ① 중복    임베딩 NULL → dedupe_skipped 로 통과
              쿼리 A: 72h·생존자(SCORED·QUEUED·SENT) 중 코사인 최댓값 ≥ 0.96 → FILTERED_OUT(dup)
              쿼리 B: 72h·상태 무관·≥ 0.88 전부 → 클러스터 상속, mention_count(다른 소스 수 + 1)
              버전 토큰 집합이 다르면 중복을 관련로 강등
    ② exclude 키워드·도메인 → FILTERED_OUT
    생존자 목록에 추가

  2국면 — 25건씩 배치
    _existing_relevance()   이전 잡에서 선별만 끝난 항목은 결정 행 재사용, 호출 안 함
    항목마다 nearest_feedback(k=2) → 유사 피드백 줄
    _triage_once: reserve_call("triage") → call_triage → parse_triage
      예약 None        → _CapReached, 루프 종료 (NEW 유지)
      배치 실패(파싱·개수·idx) → 1회 재시도(새 예약). 그래도 실패 → 기반 실패로
      기반 실패(SDK 예외)   → 결정 행 없이 NEW. 연속 2배치면 운영 알림 후 종료
      항목 실패(idx 누락·범위 밖) → triage_error 기록. 같은 항목 2회면 DROPPED
    성공 항목 → decisions(triage, relevance, reason, batch_id)

  3국면 — 항목별 savepoint (선별 결과 있고 NEW 인 것만)
    ④ 점수    src(trust_adjusted 우선)·rel·hot·multi·fresh ≥ 0.45 → 미달 DROPPED
    ⑤ 보강    body_for_judge: 300자 미만이면 원문 → trafilatura
    reserve_call("judge") None → 종료 (NEW 유지, 선별 결과는 다음 잡이 재사용)
    ⑥ 판정    nearest_feedback(k=3) 주입 → messages.parse → summaries
              false → DROPPED / true → SCORED
커밋
```

SDK 는 `max_retries=0`. 재시도는 예약 없이 나가면 상한을 깨므로 기반 실패로 흘려 다음 잡이 새 예약으로 다시 한다.

## 4. 발송 — `run_notify()` + 탐색 슬롯

```
session_scope() 열기
  최대 20회: _claim_one (LIMIT 1, FOR UPDATE SKIP LOCKED)
    now = 지금                                   ← 항목마다 새로 읽는다 (자정 경계)
    decide(importance, now)
      importance ≤ 2 → feed 기록, SENT / 무음 시간 push → QUEUED / 상한 초과 → SILENT
    DiscordNotifier.send → notifications, SENT   RateLimited → break, 그 외 예외 → FAILED
    커밋                                          ← 항목 하나 = 트랜잭션 하나

  _explore(now=지금)                              ← 예외는 rollback + 경고, 발송 결과엔 영향 없음
    무음 시간이거나 오늘 explore 발송 있음 → 끝
    후보: DROPPED · Summary 없음 · 0.35 ≤ score < 0.45 · 24h 이내 · 마지막 결정 행이 score 탈락 · 최고점
    body_for_judge → reserve_call("explore") (판정 예산 공유, 자체 상한 3/일) → 판정
    Summary 저장, category 갱신
      false → 커밋. 같은 후보는 다시 안 봄. 오늘 슬롯은 안 씀
      true  → 🧪 머리말 silent 발송 → notifications(explore) → SENT → 커밋
```

**게이트** — 디스코드 429 는 프로세스 전역 `_blocked_until`. 1초 미만 남았으면 마저 자고 진행한다(Windows 타이머 조기 기상 대응).

## 5. 피드백 — 디스코드 인터랙션

`POST /webhook/discord` Ed25519 검증 → PING 응답 / 버튼 → `upsert_feedback` (항목당 1건, 재클릭은 덮어씀) → ephemeral 답장. 이 피드백이 다음 선별·판정의 "유사 피드백" 이 되고, 주간 리포트의 소스 신뢰도 보정 입력이 된다.

## 6. 예약·상한 — `reserve_call(kind)`

```
독립 세션, 한 트랜잭션
  pg_advisory_xact_lock(단일 고정 키)
  now = DB now()                                  ← 범위 계산과 called_at 에 같은 값
  오늘(Asia/Seoul) 예산 행 수 ≥ 상한 → None
  kind 별 자체 상한(explore 3) 검사
  llm_calls 삽입, 커밋 → batch_id
```

예산: triage(60) / judge(300, explore 포함). 호출 전에 커밋되므로 실패한 호출도 세어진다.

## 상태 전이

```
NEW ──stale──▶ DROPPED
NEW ──dup/exclude──▶ FILTERED_OUT
NEW ──관문 통과──▶ (선별) ──▶ (점수) ──미달──▶ DROPPED ──탐색 1건/일──▶ (판정) ──true──▶ SENT(explore)
                                └─통과──▶ (판정) ──false──▶ DROPPED
                                                └─true──▶ SCORED ──상한/무음──▶ QUEUED
                                                                 └─발송──▶ SENT / FAILED
```

`FILTERED_OUT` 과 `DROPPED` 는 다른 종단 분기다. 재처리 대상은 `NEW` 뿐이다.

## 동시성

| 항목 | 지금 |
|---|---|
| 프로세스 | 1개. 배치 잠금을 외부 호출 동안 유지해 중복 호출이 없다 |
| 잡 겹침 | `max_instances=1`. 파이프라인 판정과 발송 잡 탐색 판정은 교차 가능 → `reserve_call` 자문 잠금이 상한을 지킴 |
| 큐 | `items.status` + `FOR UPDATE SKIP LOCKED` |
| 커넥션 | 잡 하나 = 세션 하나. 예약만 독립 세션 |
| 워커 분리 시 | 임대 컬럼, 탐색 슬롯 일자 유니크, 디스코드 429 게이트 공유가 함께 필요 (비목표) |
