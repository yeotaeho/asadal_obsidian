# 기술 파악 (tech-radar) 코드베이스 분석

## 0. 먼저 알아야 할 전제

이 프로젝트에는 **Service / Repository 계층이 존재하지 않습니다.** 요청하신 `Endpoint → Router → Service → Repository → Model → DB` 체인은 실제 코드에 없고, 대신 아래 계층으로 대응됩니다. 아래 모든 흐름은 이 대응표를 기준으로 추적했습니다.

|요청하신 계층|이 프로젝트의 실제 계층|위치|
|---|---|---|
|Endpoint / Router|FastAPI `APIRouter`|[app/api/](https://claude.ai/epitaxy/app/api/)|
|Service|Job 함수 (`run_source`, `run_pipeline`, `run_notify`)|[app/jobs/](https://claude.ai/epitaxy/app/jobs/)|
|Domain logic|파이프라인 관문 함수|[app/pipeline/](https://claude.ai/epitaxy/app/pipeline/)|
|Repository|**없음.** SQLAlchemy `select()` 를 잡·엔드포인트에서 직접 작성|각 호출부|
|Model|SQLAlchemy ORM 모델|[app/db/models.py](https://claude.ai/epitaxy/app/db/models.py)|
|DB|Neon Postgres (asyncpg)|[app/db/session.py](https://claude.ai/epitaxy/app/db/session.py)|

레포지토리 계층이 없는 것은 실수가 아니라 의도입니다. `FOR UPDATE SKIP LOCKED` 같은 잠금 구문이 쿼리에 직접 들어가야 해서, 한 겹 감싸면 잠금 범위가 감춰집니다. 실제로 [app/jobs/notify.py:24](https://claude.ai/epitaxy/app/jobs/notify.py:24) 의 `_claim_one` docstring이 그 이유를 코드에 남겨 두었습니다.

## 1. 프로젝트 전체 목적

**개인용(1인) 개발 트렌드 알림 봇**입니다. 여러 소스에서 새 글·릴리즈·영상을 주기적으로 긁어오고, 4단계 관문을 통과한 것만 텔레그램으로 밀어 줍니다.

목적은 "다 모아 보여주기"가 아니라 **"안 읽어도 되는 걸 버리기"** 입니다. 코드 전체가 관문(gate) 구조로 짜여 있고, 통과·탈락 판정은 전부 `decisions` 테이블에 남깁니다 — [app/jobs/pipeline.py:24](https://claude.ai/epitaxy/app/jobs/pipeline.py:24) `_record()` 가 이 기록을 만드는 유일한 함수입니다.

목적을 가장 직접적으로 보여주는 코드는 [app/config.py:64](https://claude.ai/epitaxy/app/config.py:64) `Rules` 와 [config/rules.yaml](https://claude.ai/epitaxy/config/rules.yaml) 입니다. 관심사(`interests`)·키워드·가중치·발송 상한이 전부 YAML 한 파일에 모여 있고, 코드에는 임계값이 하드코딩돼 있지 않습니다.

비목표는 명확합니다. 회원가입·다중 사용자·커뮤니티 기능이 없고, 그래서 **사용자 인증 코드가 아예 없습니다** (9장 참고).

## 2. 전체 아키텍처

**프로세스 1개 + Neon(Postgres) 1개.** 큐도 Redis도 없습니다.

```
                    ┌──────────────── 컨테이너 app (프로세스 하나) ────────────────┐
                    │                                                              │
 GitHub webhook ───▶│  FastAPI (app/main.py)          APScheduler (같은 이벤트루프) │
 Telegram webhook ─▶│    ├ /health                      ├ source:<name>  (N개)     │
                    │    ├ /webhook/github              ├ pipeline  (120초)        │
                    │    └ /webhook/telegram            └ notify    (180초)        │
                    │              │                              │                │
                    └──────────────┼──────────────────────────────┼────────────────┘
                                   ▼                              ▼
                            ┌──────────────────────────────────────────┐
                            │  Neon Postgres — 상태의 단일 진실 원천     │
                            │  items.status 가 곧 큐 (SKIP LOCKED)      │
                            └──────────────────────────────────────────┘
```

핵심 설계 결정 3가지를 코드에서 확인했습니다.

**① 큐를 DB로 대체.** `items.status` 컬럼이 큐 상태이고, 워커는 `SELECT ... FOR UPDATE SKIP LOCKED` 로 집습니다. [app/jobs/pipeline.py:36](https://claude.ai/epitaxy/app/jobs/pipeline.py:36) `_claim_batch()` 와 [app/jobs/notify.py:24](https://claude.ai/epitaxy/app/jobs/notify.py:24) `_claim_one()` 둘 뿐입니다.

**② 스케줄러가 API와 같은 프로세스.** [app/main.py:19](https://claude.ai/epitaxy/app/main.py:19) `lifespan()` 이 `start_scheduler()` 를 호출합니다. 별도 워커 컨테이너가 없습니다.

**③ 플러그인 = 프로토콜 + 레지스트리.** 소스도 발송 채널도 상속이 아니라 `Protocol` 만족 여부로 정의됩니다 — [app/sources/base.py:19](https://claude.ai/epitaxy/app/sources/base.py:19) `Source`, [app/notify/base.py:11](https://claude.ai/epitaxy/app/notify/base.py:11) `Notifier`.

파이프라인 흐름은 이렇습니다.

```
소스 fetch ─▶ store_items ─▶ [NEW]
                               │
                     ┌─────────┴─────────┐  run_pipeline (120초마다)
                     │ ① 중복 (find_cluster)     → FILTERED_OUT
                     │ ② 규칙 (apply_rules)      → FILTERED_OUT
                     │ ③ 점수 (score_item)       → DROPPED
                     │ ④ LLM  (llm.judge)        → DROPPED
                     └─────────┬─────────┘
                               ▼
                            [SCORED] ─▶ run_notify (180초마다)
                                          decide() ─┬─ push/silent ─▶ 텔레그램 ─▶ [SENT]
                                                    ├─ feed_only         ─────────▶ [SENT] (발송 안 함)
                                                    ├─ quiet_hours ─────────────▶ [QUEUED] (아침에 재시도)
                                                    └─ 발송 예외 ───────────────▶ [FAILED]
```

### 가장 중요한 도메인 개념 — `ItemStatus`

[app/schemas.py:21](https://claude.ai/epitaxy/app/schemas.py:21) 의 7가지 상태가 사실상 이 앱의 상태 기계 전부입니다.

```
NEW ─┬─ 제목 유사도 > 0.6      ──▶ FILTERED_OUT  (dedupe)
     ├─ exclude 키워드/도메인  ──▶ FILTERED_OUT  (rules)
     ├─ 점수 < 0.45            ──▶ DROPPED       (scoring)
     ├─ LLM worth=false        ──▶ DROPPED       (llm)
     └─ 통과                   ──▶ SCORED
                                    │
SCORED ─┬─ importance ≤ 2      ──▶ SENT   (feed — 발송 안 하고 기록만)
        ├─ 무음시간(23~08 KST) ──▶ QUEUED (다음 잡에서 재시도)
        ├─ 발송 성공           ──▶ SENT
        └─ 발송 예외           ──▶ FAILED
```

`FILTERED_OUT`(값어치 없음)과 `DROPPED`(점수 미달)를 나눈 게 포인트입니다. 나중에 임계값을 낮췄을 때 `DROPPED` 만 다시 볼 수 있습니다.

### 중복 제거는 2단계

- **1단계 — 정확 중복.** `url_hash` UNIQUE. [app/pipeline/normalize.py:17](https://claude.ai/epitaxy/app/pipeline/normalize.py:17) `normalize_url()` 이 utm 파라미터·`www.`·트레일링 슬래시를 제거하고 쿼리를 **정렬**한 뒤 SHA-256을 뜹니다. 정렬 때문에 `?a=1&b=2` 와 `?b=2&a=1` 이 같은 해시가 됩니다.
- **2단계 — 유사 중복.** [app/pipeline/dedupe.py:16](https://claude.ai/epitaxy/app/pipeline/dedupe.py:16) `find_cluster()` 가 pg_trgm `similarity()` 로 72시간 내 제목 유사도 0.6 초과 항목을 찾아 `cluster_id` 로 묶습니다. 같은 뉴스를 3개 매체가 다루면 1개만 남고, 나머지 2개는 `mention_count` 를 올려 **점수를 높이는 데 기여**합니다 ([scoring.py:40](https://claude.ai/epitaxy/app/pipeline/scoring.py:40) 의 `multi` 항).

### `_process()` — 가장 먼저 읽어야 할 함수

[app/jobs/pipeline.py:49](https://claude.ai/epitaxy/app/jobs/pipeline.py:49). 88줄이지만 이 앱의 비즈니스 로직 대부분이 여기 있습니다. 구조는 단순한 early-return 4연속입니다.

```python
# ① 중복 → FILTERED_OUT
cluster_id = await find_cluster(session, item.title, exclude_item_id=item.id)
if cluster_id is not None: ... return False

# ② 규칙 → FILTERED_OUT
verdict = apply_rules(rules, source=..., title=..., body=..., url=..., repo=...)
session.add(_record(item, Stage.RULE, verdict.passed, {...}))
if not verdict.passed: ... return False

# ③ 점수 → DROPPED
score = score_item(rules.scoring, trust=source.trust_score, ...)
session.add(_record(item, Stage.SCORE, score.passed, {"breakdown": score.breakdown}))
if not score.passed: ... return False

# ④ 본문 보강 후 LLM → DROPPED 또는 SCORED
if not body or len(body) < llm.ENRICH_MIN_CHARS:
    enriched = await llm.enrich_body(item.url)      # trafilatura
result = await llm.judge(rules, source=..., title=..., body=body)
```

반환값이 `bool` 인 게 중요합니다. **"LLM을 실제로 호출했는가"** 를 뜻하고, 호출부 `run_pipeline()` 이 이걸로 일일 예산을 깎습니다.

### 점수화 공식

[app/pipeline/scoring.py:40](https://claude.ai/epitaxy/app/pipeline/scoring.py:40) `score_item()`. 5개 항의 가중합이고 가중치는 [config/rules.yaml](https://claude.ai/epitaxy/config/rules.yaml) 에 있습니다.

|항|계산|가중치|의미|
|---|---|---|---|
|`src`|`trust_score` 그대로|0.25|소스 신뢰도 (anthropic 1.0, arxiv 0.5)|
|`kw`|`min(hits, 3) / 3`|0.25|키워드 매칭 (3개에서 포화)|
|`hot`|`hotness(metrics)`|0.2|소스가 준 인기 지표|
|`multi`|`min(mentions-1, 2) / 2`|0.2|여러 소스 언급|
|`fresh`|반감기 24h 지수감쇠|0.1|신선도|

합이 `threshold` (0.45) 이상이면 통과합니다. `breakdown` 딕셔너리가 `decisions.details` 에 통째로 저장돼서, 나중에 "왜 이건 떨어졌지"를 SQL로 조회할 수 있습니다.

```python
@asynccontextmanager
async def session_scope() -> AsyncIterator[AsyncSession]:
    """잡 하나 = 세션 하나. 성공 시 커밋, 예외 시 롤백."""
    async with SessionLocal() as session:
        try:

            await session.commit()
        except Exception:
            await session.rollback()
            raise
```

## 9. 인증 / 인가 구조

**사용자 인증이 없습니다.** 로그인·세션·JWT·RBAC 관련 코드가 코드베이스에 한 줄도 없습니다. `user_prefs` 테이블조차 마이그레이션에 없습니다(YAML로 대체).

단일 사용자용 앱이라 의도된 설계입니다. 대신 **외부에서 들어오는 요청을 검증하는 장치가 3개** 있습니다.

|#|대상|방식|위치|실패 시|
|---|---|---|---|---|
|1|GitHub 웹훅 (수신)|HMAC-SHA256 서명 검증|[api/github.py:22](https://claude.ai/epitaxy/app/api/github.py:22) `verify_signature()`|401|
|2|Telegram 웹훅 (수신)|시크릿 토큰 헤더 비교|[api/telegram.py:26](https://claude.ai/epitaxy/app/api/telegram.py:26) 인라인|401|
|3|GitHub API (송신)|`Authorization: Bearer <PAT>`|[sources/github_release.py](https://claude.ai/epitaxy/app/sources/github_release.py) `auth_headers()`|레이트리밋|

### ① GitHub 웹훅 서명 검증

```python
# app/api/github.py:22
def verify_signature(body: bytes, signature: str | None) -> bool:
    secret = get_settings().github_webhook_secret
    if not secret or not signature:
        return False                                     # ← fail-closed
    expected = "sha256=" + hmac.new(secret.encode(), body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, signature)
```

세 가지가 제대로 돼 있습니다. **원본 바이트**(`await request.body()`)로 검증하고, `compare_digest` 로 타이밍 공격을 막고, 시크릿 미설정 시 **통과가 아니라 거부**합니다.

### ② Telegram 웹훅 시크릿

```python
# app/api/telegram.py:26
secret = get_settings().telegram_webhook_secret
if not secret or not hmac.compare_digest(secret, x_telegram_bot_api_secret_token or ""):
    raise HTTPException(status_code=401, detail="secret token mismatch")
```

`setWebhook` 시 등록한 `secret_token` 을 텔레그램이 매 요청 헤더에 넣어 주는 방식입니다. 마찬가지로 fail-closed입니다.

### ③ 토큰 유출 방지

봇 토큰이 URL 경로에 들어가는 구조라 예외 메시지로 새기 쉽습니다. [app/notify/telegram.py:55](https://claude.ai/epitaxy/app/notify/telegram.py:55) `_call()` 이 이걸 차단합니다.

```python
except httpx.HTTPStatusError as exc:
    raise RuntimeError(f"telegram {method} HTTP {exc.response.status_code}") from None
```

`from None` 으로 원인 체인을 끊어 URL이 담긴 원본 예외를 감춥니다. [tests/test_telegram_api.py](https://claude.ai/epitaxy/tests/test_telegram_api.py) 에 3개 테스트로 고정돼 있습니다.

### 인증 관련 주의점

- **`GET /health` 는 완전 공개입니다.** DB 상태만 노출하니 현재는 문제없습니다.
- **`/webhook/*` 는 Caddy가 그대로 통과시킵니다.** [Caddyfile](https://claude.ai/epitaxy/Caddyfile) 은 `reverse_proxy app:8000` 뿐이라 IP 화이트리스트가 없습니다. 검증은 전적으로 앱 코드 책임입니다.
- **읽기 API(3단계 예정)를 추가할 때 인증 설계가 처음 필요해집니다.** 현재는 참고할 기존 패턴이 없습니다.


# 신입 개발자용 정리

## 프로젝트 5줄 요약

1. 개발 트렌드 소스(RSS·GitHub 릴리즈·YouTube)를 주기적으로 긁어 Neon Postgres에 적재하고, 읽을 가치가 있는 것만 텔레그램으로 푸시하는 **1인용 알림 봇**이다.
2. **FastAPI + APScheduler가 한 프로세스**에서 돌고, DB는 Neon 하나뿐이며, `items.status` 컬럼이 `FOR UPDATE SKIP LOCKED` 와 함께 **큐 역할을 겸한다**(Redis·MQ 없음).
3. 모든 항목은 **중복 → 규칙 → 점수 → LLM** 4단계 관문을 통과해야 하고, 통과·탈락 판정은 전부 `decisions` 테이블에 기록된다.
4. **LLM은 마지막 관문에서 한 번만** 호출되며([pipeline/llm.py:70](https://claude.ai/epitaxy/app/pipeline/llm.py:70) `judge()`), 하루 호출 상한(기본 300)을 `summaries` 행 수로 관리한다.
5. 소스와 발송 채널은 **Protocol + 레지스트리 플러그인**이라, 새 소스를 추가하려면 파일 하나에 `@register("타입명")` 만 붙이면 된다.

## 처음 공부해야 할 기능 3개

### ① `items.status` 상태 기계와 SKIP LOCKED 큐

**왜 먼저인가.** 이걸 모르면 다른 코드가 전부 안 읽힙니다. "왜 큐를 안 쓰지?"라는 의문이 이 하나로 풀립니다.

**볼 곳.** [app/schemas.py:21](https://claude.ai/epitaxy/app/schemas.py:21) `ItemStatus` → [app/jobs/pipeline.py:36](https://claude.ai/epitaxy/app/jobs/pipeline.py:36) `_claim_batch` → [app/jobs/notify.py:24](https://claude.ai/epitaxy/app/jobs/notify.py:24) `_claim_one`.

**직접 해볼 것.** `_claim_one` docstring을 읽고, "20건을 한 번에 잠그면 왜 중복 발송이 나는가"를 자기 말로 설명해 보세요. 여기가 이 코드베이스에서 가장 미묘한 부분입니다.

### ② 4단계 관문 파이프라인

**왜.** 이 앱이 존재하는 이유 자체입니다. 앞으로 하게 될 작업의 90%가 "관문을 조정하는 일"입니다.

**볼 곳.** [app/jobs/pipeline.py:49](https://claude.ai/epitaxy/app/jobs/pipeline.py:49) `_process()` 를 위에서 아래로 한 줄씩 → 각 관문 구현([dedupe.py:16](https://claude.ai/epitaxy/app/pipeline/dedupe.py:16), [rules.py:49](https://claude.ai/epitaxy/app/pipeline/rules.py:49), [scoring.py:40](https://claude.ai/epitaxy/app/pipeline/scoring.py:40), [llm.py:70](https://claude.ai/epitaxy/app/pipeline/llm.py:70)).

**직접 해볼 것.** `config/rules.yaml` 의 `threshold` 를 0.45 → 0.2 로 낮추고 `run_job.py pipeline` 을 돌린 뒤, `decisions` 에서 `stage='score'` 행의 `details.breakdown` 을 조회해 어떤 항이 점수를 만들었는지 보세요.

### ③ 소스 플러그인 추가

**왜.** 이 코드베이스에서 가장 흔한 작업이고, 다른 계층을 안 건드려도 되는 안전한 첫 기여입니다.

**볼 곳.** [app/sources/base.py:32](https://claude.ai/epitaxy/app/sources/base.py:32) `register` → [app/sources/youtube.py](https://claude.ai/epitaxy/app/sources/youtube.py) (18줄, 재사용 예시) → [app/sources/**init**.py](https://claude.ai/epitaxy/app/sources/__init__.py) (import 없으면 등록 안 됨).

**직접 해볼 것.** Hacker News 수집기(`hackernews.py`)를 추가해 보세요. CLAUDE.md 계획에 있으나 아직 구현되지 않았고, Algolia `search_by_date` API가 페이지네이션 없이 JSON을 주므로 난이도가 적당합니다. `@register("hackernews")` + `config/sources.yaml` 항목 추가 + `tests/fixtures/` 샘플 + respx 테스트까지가 한 세트입니다.

## 아직 파악하지 못한 부분

정직하게 구분해 적습니다.

### 코드를 읽어서는 알 수 없는 것 (운영 정보)

- **Neon DB의 실제 상태.** 마이그레이션이 적용됐는지, `items` 에 데이터가 얼마나 쌓였는지, 파이프라인이 실제로 돌고 있는지 확인하지 않았습니다. 확인하려면 `neon-db` MCP나 psql이 필요합니다.
- **웹훅이 실제로 등록돼 있는지.** GitHub 저장소 설정과 텔레그램 `setWebhook` 은 코드 밖 작업입니다. 이걸 하는 스크립트나 문서가 저장소에 없습니다.
- **배포 상태.** `.github/workflows/ci.yml` 은 VM SSH 배포를 정의하지만 `secrets.VM_HOST` 등이 설정됐는지, 실제로 배포된 적 있는지는 모릅니다.
- **LLM 프롬프트의 실효성.** [llm.py](https://claude.ai/epitaxy/app/pipeline/llm.py) `SYSTEM_PROMPT`/`USER_TEMPLATE` 는 읽었지만, 실제로 어떤 판정을 내리는지는 돌려 봐야 압니다.

### 확인했으나 검증하지 않은 것

- **테스트를 실행하지 않았습니다.** 55개 테스트가 있고 CI에 걸려 있지만, 이번 분석에서 `pytest` 를 돌리지 않았습니다. 요청 범위가 분석이었고 코드 변경이 없어 생략했습니다. 필요하면 바로 돌리겠습니다.
