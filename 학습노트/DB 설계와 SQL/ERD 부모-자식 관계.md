# ERD 부모-자식 관계

> [!summary] 한 줄 요약
> 부모-자식은 **"부모가 삭제되면 자식이 의미를 잃는가?"(존재 종속성)** 로 판단하고, 1:N 관계에서 **1쪽이 부모, FK를 든 N쪽이 자식**이다. RE:SEED의 산정 근거(부모) ↔ 증빙 파일(자식) 설계에서 배움.

## 부모와 자식을 나누는 기준

- **부모** — 다른 엔티티 없이 **독립적으로 존재** 가능. 자기 PK를 자식에게 빌려준다. (예: 부서, 산정 근거)
- **자식** — 부모가 있어야 성립. 부모의 PK를 **FK로 들고 있는 쪽**. (예: 사원, 증빙 파일)

방향이 헷갈릴 때의 함정 — "증빙 파일 : 산정 근거 = N:1"이라는 카디널리티 판단 자체는 맞다. 하지만 **N:1에서 부모는 N쪽이 아니라 1쪽**이다. 산정 근거가 삭제되면 증빙 파일은 "무엇을 증명하는 파일인지" 알 수 없는 쓰레기 데이터가 되므로, **산정 근거가 부모**다.

## 관계가 있는지 판단하는 세 가지 질문

1. **동사가 성립하나?** — (사용자)가 (주문)을 **한다** → 관계 있음. (날씨)가 (게시글)을...? → 없음.
2. **참조가 필요한가?** — 주문 상세만 봐서는 어떤 물건인지 모른다 → 상품 테이블과 관계 필요.
3. **중복이 생기나?** — 한 테이블에 특정 데이터가 반복되면 분리(정규화)하고 관계를 맺는다.

## 관계의 종류

| 유형 | 예 | 설계 방식 |
|---|---|---|
| 1:1 | 사용자 - 프로필 | 한쪽에 FK 또는 PK 공유 |
| 1:N | 산정 근거 - 증빙 파일 | **N(자식) 쪽이 FK를 가짐** |
| N:M | 학생 - 수업 | 직접 연결 불가 → **[[Junction Table — 다대다를 두 개의 1대N으로|Junction Table(중간·매핑 테이블)]]** 생성 |

N:M의 중간 테이블은 양쪽 FK 두 개를 묶어 복합 PK로 잡는 경우가 많다 → [[PK·FK와 복합키]]. "파일 하나가 여러 산정 근거에 재사용된다"면 1:N이 아니라 이 구조가 필요해진다.

## 존재 종속성 — 관계의 강도

| 구분 | 식별 관계 (실선) | 비식별 관계 (점선) |
|---|---|---|
| 의미 | 부모 없이 **절대 존재 불가** | 부모가 없어도 독립 존재 가능 |
| FK 위치 | 부모 PK가 자식 **PK의 일부** | 부모 PK가 자식의 **일반 속성(FK)** |
| 부모 삭제 시 | 자식도 같이 삭제돼야 논리가 맞음 | 자식은 남겨둘 수 있음 |
| 예 | 붕어빵 틀 - 붕어빵 | 부서 - 사원 (부서가 없어져도 사원은 남음) |

실무 판단 도구는 **`ON DELETE CASCADE`를 걸 것인가**라는 질문이다. "부모를 지울 때 자식도 자동 삭제할까?"에 Yes면 강한 부모-자식 관계, No면 약한 관계다.
