# JOIN은 왜 하는가

> [!summary] 한 줄 요약
> JOIN의 근본 이유는 **"쪼개서 저장하고(정규화), 합쳐서 보기 위해서"** 다. 저장은 중복 없이 효율적으로, 조회는 완성된 정보로 — JOIN은 그 둘 사이의 다리다.

## 쪼개는 이유 — 정규화와 무결성

산정 근거 테이블에 증빙 파일 정보를 다 넣으면, 파일이 5개일 때 같은 근거 데이터가 **5번 중복 저장**된다. 그래서 분리한다.

- **수정의 편의** — 금액이 바뀌면 중복된 모든 행이 아니라 **부모 테이블 한 줄**만 고친다.
- **삭제의 안전** — 관계를 맺어두면 근거 없는 파일, 파일 없는 근거 같은 꼬임을 막는다.

> 장부 매 줄마다 영수증 사진을 통째로 붙이는 대신, 장부엔 **영수증 번호(FK)** 만 적고 영수증은 보관함에 따로 둔다. 필요할 때 번호를 대조해 꺼내오는 행위가 **JOIN**이다.

## 필요할 때만 JOIN하는 네 가지 레벨

항상 JOIN하면 무거워진다. 상황별로 레벨을 골라 쓴다.

| 레벨 | 방법 | 언제 |
|---|---|---|
| SQL | `EXISTS` 서브쿼리 | "연관 데이터가 **있는지**"만 볼 때 — 합치는 비용 없음 |
| 애플리케이션 | **Lazy Loading** (JPA·SQLAlchemy) | 기본값. 자식에 실제 접근하는 시점에만 쿼리 발생 |
| DB 설계 | 역정규화 — `has_file`·`file_count` 플래그 | 유무 확인이 매우 빈번할 때. 단, 갱신 로직 필요 |
| 아키텍처 | API 분리 (목록 API + 클릭 시 상세 API) | 프론트가 단계적으로 데이터를 쓰는 화면 |

```sql
-- 증빙 파일이 존재하는 산정 근거만 — JOIN보다 가볍다
SELECT * FROM calculation_basis cb
WHERE EXISTS (SELECT 1 FROM evidence_files ef WHERE ef.basis_id = cb.id);
```

데이터가 많은 프로젝트라면 **기본은 Lazy Loading, 대량 통계 화면만 최적화된 JOIN 쿼리**를 따로 작성하는 조합이 권장된다.

## JOIN 조건은 컬럼 여러 개도 된다

컬럼 하나로 행을 특정할 수 없으면 `AND`로 연결 고리를 늘린다. (사업장ID, 년도, 월)이 모두 일치해야 하는 배출 로그 ↔ 월별 목표치가 그 예 — 사업장ID로만 JOIN하면 1월 로그가 전체 월 목표와 다 붙어버린다.

```sql
JOIN monthly_targets t
  ON  log.business_id = t.business_id
  AND log.year  = t.year
  AND log.month = t.month
```

주의 — 양쪽 컬럼의 **데이터 타입이 일치**해야 하고, 다중 컬럼 JOIN엔 **복합 인덱스**가 있어야 빠르다.
