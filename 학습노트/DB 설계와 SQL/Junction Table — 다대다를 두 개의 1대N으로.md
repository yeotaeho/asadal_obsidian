# Junction Table — 다대다를 두 개의 1대N으로

> [!summary] 한 줄 요약
> Junction Table(교차·매핑 테이블)은 **N:M 관계를 두 개의 1:N 관계로 분해**하는 다리 테이블이다. 양쪽 PK를 FK로 가져와 복합 PK로 묶고, "관계 자체의 정보"(등록일·성적 등)를 담는 자리이기도 하다.

## 왜 필요한가

학생과 수업의 관계를 보면 — 한 학생은 **여러** 수업을 듣고, 한 수업엔 **여러** 학생이 있다. 이 N:M을 직접 이으려고 학생 테이블에 수업 ID를 넣거나 수업 테이블에 학생 ID를 넣으면 **데이터가 중복되거나 관리가 불가능**해진다.

해법은 중간에 '수강신청(Enrollment)' 테이블을 두는 것이다.

```
학생 (1) ──< 수강신청 (Enrollment) >── (1) 수업
          N:M  →  1:N 두 개로 분해
```

## 구조적 특징

- **FK 두 개** — 연결하려는 두 테이블의 PK를 각각 FK로 가져온다.
- **복합 PK** — 두 FK의 조합을 이 테이블의 PK로 쓰는 경우가 많다. → [[PK·FK와 복합키]]
- **관계의 추가 정보** — 단순 연결을 넘어 '등록 일자', '성적'처럼 **관계 자체에 속하는 데이터**를 저장하기 좋은 자리다. (학생에도 수업에도 속하지 않는 정보)

## 예시 — 수강 신청

Student(1 김철수, 2 이영희)와 Class(A1 데이터베이스, B2 알고리즘)를 잇는 Enrollment 테이블.

| StudentID (FK) | ClassID (FK) | EnrollmentDate |
|---|---|---|
| 1 | A1 | 2026-02-01 |
| 1 | B2 | 2026-02-01 |
| 2 | A1 | 2026-02-02 |

**행 하나가 연결 하나**다 — 김철수(1)는 두 수업을 듣고, 데이터베이스(A1)엔 두 학생이 있다. (StudentID, ClassID) 조합이 복합 PK라서 같은 수강신청의 중복 등록도 막힌다.

## 핵심

> **얽힌 N:M을 두 개의 1:N으로 분해**해 데이터 무결성을 지키고 효율적인 JOIN을 가능하게 한다.

RE:SEED 설계에 적용하면 — "증빙 파일 하나가 여러 산정 근거에 재사용"되는 요구가 생기는 순간, [[ERD 부모-자식 관계|1:N 구조]]로는 안 되고 이 구조가 필요해진다.
