# PK·FK와 복합키

> [!summary] 한 줄 요약
> **PK는 테이블당 무조건 하나**지만 그 하나가 여러 컬럼의 조합(복합키)일 수 있고, **FK는 PK가 아니어도 되지만 반드시 Unique 컬럼**만 참조할 수 있다.

## "PK가 여러 개"의 진짜 의미 — 복합키

PK라는 제약 조건은 테이블당 딱 하나다. "여러 개 가진다"는 말은 보통 **복합키(Composite Key)** — 2개 이상 컬럼을 묶어 하나의 PK로 쓰는 것 — 를 뜻한다.

> 자물쇠가 2개인 문(각각 열어야 함)이 아니라, **비밀번호가 두 자리인 금고**(둘 다 맞아야 열림)다.

성적 테이블이 대표 예 — `학생ID`만 PK면 학생당 한 과목만 저장되고, `과목코드`만 PK면 과목당 한 명만 수강 가능하다. `학생ID + 과목코드` 조합이어야 (학생A, 수학)·(학생A, 영어)는 통과하고 (학생A, 수학) 재삽입만 막힌다.

## 복합키를 쓰는 곳, 피하는 곳

- **N:M 매핑 테이블** — 양쪽 FK 두 개를 묶어 PK로. → [[Junction Table — 다대다를 두 개의 1대N으로]]
- **식별 관계** — 부모 PK가 자식 PK의 일부가 되는 강한 결합. → [[ERD 부모-자식 관계]]
- **피하는 경우** — 복합키 컬럼이 4~5개로 늘면 JOIN 쿼리가 복잡해지고 성능이 떨어진다. 실무에선 **인공키(Auto-Increment id)를 PK로 잡고, 복합 컬럼엔 `UNIQUE` 제약**을 거는 방식을 선호한다.

## FK는 PK가 아니어도 되나?

**된다 — 단, 참조 대상이 반드시 `UNIQUE`여야 한다.** FK의 목적은 "정확히 어떤 부모 행을 가리키는지"인데, `작성자_성함` 같은 중복 가능 컬럼을 참조하면 홍길동이 두 명일 때 연결이 깨진다. DB 엔진이 Unique 없는 컬럼 참조를 아예 거부한다.

PK 대신 Unique 일반 컬럼을 참조하는 실무 사례는 두 가지다.

- **비즈니스 키(Natural Key)** — 내부용 id 숫자 대신 `로그인_ID`, `사업자_번호`처럼 현실의 고유값으로 연결.
- **가독성** — 조인 결과만 보고도 무슨 데이터인지 알 수 있는 사람용 코드(`공정_코드` 등).

그래도 **특별한 이유가 없으면 PK 참조가 정석**이다 — PK는 인덱스가 자동 생성되고 성능·안전성 모두 유리하다. 일반 Unique 컬럼을 쓸 땐 양쪽 **데이터 타입 일치**를 반드시 확인.
