# 클라우드에서의 Ollama

> [!summary] 한 줄 요약
> AWS에서도 Ollama의 기본 조합은 로컬과 동일한 **"컴퓨팅(GPU) + 고속 블록 스토리지(EBS)"** 다. **S3는 속도 때문에 실행용 디스크가 될 수 없고**, 모델 원본을 보관했다가 부팅 시 내려받는 **창고(Model Registry)** 역할을 맡는다.

## S3에서 직접 실행할 수 없는 이유

LLM은 수십억 파라미터를 초고속 연산해야 하므로 모델을 **VRAM/RAM에 통째로 올려놓고** 계산한다. S3는 네트워크 기반 객체 스토리지라 실시간 연산용 디스크로 쓰기엔 너무 느리다. 즉 "S3로 연결해 실행"이 아니라, **S3 → 로컬 디스크(EBS) → VRAM** 순서로 옮겨 실행한다.

## 배포 방식 두 가지

### ① EC2 (가상 머신) — 로컬을 그대로 옮긴 형태

- GPU 인스턴스(`g4dn`, `g5` 시리즈) 생성.
- 로컬 SSD 역할의 **EBS** 볼륨에 올라마와 모델 파일(GGUF) 저장.
- 접속해서 `ollama run` → EBS의 모델이 VRAM으로 로드되고 11434 API가 열린다. [[Ollama 실행 구조와 CLI|로컬과 동일한 구조]]다.

### ② Docker + ECS/EKS (컨테이너) — 프로덕션 형태

- 공식 이미지 `ollama/ollama`를 ECS나 EKS(Kubernetes)에 배포.
- 컨테이너가 재생성돼도 모델이 사라지지 않도록 모델 경로(`/root/.ollama`)를 **EBS나 EFS에 마운트**해 영구 저장소로 쓴다.

## S3의 진짜 역할 — 모델 레지스트리 파이프라인

GPU 붙은 EBS는 유지 비용이 비싸다. 그래서 크고 저렴한 S3를 원본 창고로 쓴다.

```
S3 버킷 (커스텀 Modelfile·GGUF 보관, 저렴)
   │  인스턴스/컨테이너 부팅 시 시작 스크립트(User Data)가
   ▼  aws s3 cp 로 다운로드
EBS (로컬 디스크)
   ▼  올라마가 읽어서 로드
VRAM → 서빙 시작
```

## 백엔드와의 연결 — 보안

- **보안 그룹** — 11434 포트를 열되, `0.0.0.0/0` 전체 공개 대신 **백엔드 서버 IP나 VPC 내부 대역만** 허용.
- **ALB 연동** — 올라마 앞에 Application Load Balancer + SSL을 두고 도메인(`https://api.my-llm-server.com/v1`) 형태로 통신하는 것이 표준 아키텍처.
