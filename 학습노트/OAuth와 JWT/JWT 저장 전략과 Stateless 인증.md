# JWT 저장 전략과 Stateless 인증

> [!summary] 한 줄 요약
> Access Token은 **프론트 메모리(Zustand)**, Refresh Token은 **HttpOnly 쿠키 + 서버 장부(Redis)** 에 두는 하이브리드 전략이 정석이다. 서버는 평소엔 서명 "판독"만 하고(Stateless), 로그아웃·해킹 대응 같은 "통제"는 Refresh 장부로 한다. 발급 흐름은 [[OAuth 인가 코드 흐름과 서비스 JWT 발급]] 참고.

## 왜 토큰을 프론트로 보내는가 — 장부 vs 카드키

서버가 모든 로그인 상태를 들고 있는 세션 방식(Stateful)은 접속자가 늘수록 메모리·조회 부하가 커지고, 서버를 여러 대로 늘리면 **1번 서버에서 로그인한 유저를 2번 서버가 모른다**는 문제가 생긴다.

> 호텔 프런트의 **숙박객 장부**(세션)는 손님이 올 때마다 장부를 뒤져야 하지만, **카드키**(JWT)는 손님이 각자 들고 다니고 프런트는 "우리 호텔 마크(Secret Key 서명)가 진짜인가"만 판독한다.

"프론트와 분담"의 의미도 여기 있다. 100만 건을 프론트로 넘기는 게 아니라, **100만 명 각자가 자기 증명서 하나씩만** 들고 다니는 것. 어떤 서버로 요청이 가든 같은 Secret Key만 있으면 즉시 검증되므로 확장이 자유롭다.

단, 이건 **발급 이후** 얘기다. 최초 발급 시점엔 세션이든 토큰이든 DB(장부)를 확인하는 인증 절차가 반드시 필요하다.

## 토큰별 저장 위치

| 토큰 | 저장 위치 | 이유 |
|---|---|---|
| Access Token (수명 30분~1시간) | **프론트 메모리** (Zustand 등) | JS 변수라 XSS로 훔치기 가장 어렵고, 새로고침 시 사라져도 Silent Refresh로 복구 |
| Refresh Token (수명 2주~1달) | **HttpOnly 쿠키** | JS 접근 자체가 불가(XSS 방어), 갱신 요청 시 브라우저가 자동 전송 |
| Refresh Token 사본 | **서버 장부** (Redis/DB) | 아래 "통제권" 절 |

주의 — Zustand `persist` 미들웨어로 localStorage에 내리면 **메모리 저장의 XSS 방어 이점이 사라진다**. Access Token은 새로고침에 날아가게 두는 게 맞다.

## Refresh Token만은 서버에도 적는다 — Kill Switch

Access Token은 서버가 완전히 잊어도 되지만, Refresh Token까지 잊으면 **한번 발행된 토큰을 만료 전에 무효화할 방법이 없다**. 그래서 Refresh Token은 서버 장부에 기록해 두고, 로그아웃·해킹 의심 시 장부에서 지운다. 탈취된 Refresh Token을 들고 와도 장부에 없으면 거절된다.

장부로 Redis를 쓰는 이유는 두 가지 — 갱신마다 조회하므로 **메모리 기반이라 빠르고**, TTL 설정으로 **만료 자동 삭제**가 된다.

## Silent Refresh — 새로고침에도 로그인이 안 풀리는 이유

```
1. API 요청 → 서버 "Access Token 만료" (401)
2. 프론트 → /reissue 요청 (HttpOnly 쿠키의 RT 자동 동봉)
3. 서버: 장부의 RT와 대조 → 일치하면 새 AT 발급
4. 프론트: 새 AT를 Zustand에 저장 → 원래 요청 재시도
```

앱 구동 직후에도 같은 요청을 먼저 보내므로, 메모리가 날아간 새로고침 뒤에도 사용자는 로그아웃을 느끼지 못한다. 구현은 Axios **Response Interceptor**에서 401 감지 → 재발급 → 재시도.

## 전체 생애 주기 4단계

| 단계 | 서버가 하는 일 |
|---|---|
| ① 로그인 | DB로 본인 확인 → AT·RT 생성 → RT를 장부에 기록 → AT는 JSON, RT는 `Set-Cookie`(HttpOnly·Secure·SameSite)로 전달 |
| ② 이용 | `Authorization: Bearer AT` 서명만 검증 — **DB 조회 없음** |
| ③ 갱신 | 쿠키의 RT를 장부와 대조 → 새 AT 발급 |
| ④ 로그아웃 | 장부의 RT 삭제 → 이후 갱신 불가 |

**서버는 "최초 확인"과 "최종 통제"만 담당하고, 일상 인증은 토큰이 스스로 증명한다.** Access Token은 서버에 저장할 필요가 없다.

## 보안 체크리스트

- Payload에 **민감 정보 금지** — JWT는 서명만 됐지 암호화가 아니라 누구나 열어볼 수 있다. 유저 ID·권한 정도만.
- 쿠키에 `SameSite: Strict/Lax` — 쿠키 방식이 갖는 CSRF 위험 방어.
- `Secure` 플래그 — HTTPS에서만 전송.
- 검증 미들웨어의 공통 3단계 — 헤더에서 추출 → **서명·만료 검증** → 클레임으로 인증 객체 구성. (Spring `OncePerRequestFilter`, Express 미들웨어 함수, DRF 인증 클래스.)
