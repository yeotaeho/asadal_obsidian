# OAuth 인가 코드 흐름과 서비스 JWT 발급

> [!summary] 한 줄 요약
> 카카오 소셜 로그인은 **인가 코드 → 카카오 액세스 토큰 → 사용자 정보 → 우리 서비스 JWT**의 3단 교환이다. 인가 코드가 JWT로 "변환"되는 게 아니라, 백엔드가 카카오 정보를 확인한 뒤 **자체 Secret Key로 JWT를 직접 생성**한다. 저장 전략은 [[JWT 저장 전략과 Stateless 인증]] 참고.

## 전체 흐름 — 세 주체, 세 단계

```
① 프론트 → 백엔드   : 카카오 로그인 시작 요청
② 백엔드 → 프론트   : 카카오 인증 URL 반환
③~⑤ 프론트 ↔ 카카오 : 사용자 로그인·동의 → redirect_uri?code=XXXX 로 인가 코드 수신
⑥ 프론트 → 백엔드   : 인가 코드 전달 (POST /callback)
⑦~⑧ 백엔드 ↔ 카카오 : 인가 코드 ↔ 카카오 액세스 토큰 교환
⑨~⑩ 백엔드 ↔ 카카오 : 액세스 토큰으로 사용자 정보(JSON 프로필) 조회
⑪ 백엔드 → 프론트   : DB 조회(가입/로그인 처리) 후 우리 서비스 JWT 발급
```

핵심은 **⑦~⑩에 프론트가 관여하지 않는다**는 것. 인가 코드를 액세스 토큰으로 바꾸는 일은 client-secret을 가진 백엔드만 할 수 있다.

## ⑩의 "사용자 정보"는 JWT가 아니다

카카오가 백엔드에 주는 것은 카카오 DB에 저장된 **실제 프로필 JSON**(고유 ID, 닉네임, 이메일 등)이다. JWT는 카카오가 주는 게 아니라 **우리 백엔드가 그 정보를 근거로 직접 만들어** 프론트에 주는 것.

> 구청(카카오)에서 **주민등록등본**(사용자 정보)을 발급받고, 그 등본을 근거로 우리 헬스장(서비스)이 **회원권**(JWT)을 발급하는 관계.

## 카카오 액세스 토큰 vs 우리 서비스 JWT

| 구분 | 카카오 액세스 토큰 (⑧) | 우리 서비스 JWT (⑪) |
|---|---|---|
| 발급 주체 | 카카오 서버 | **우리 백엔드** |
| 용도 | 카카오 API 호출 (프로필 조회 등) | **우리 서비스 API** 호출 |
| 규칙 결정 | 카카오 | **개발자** (Payload 내용·만료 시간·알고리즘 전부) |

## 인가 코드의 정체

무작위로 생성된 긴 문자열로, **일회성 임시 비밀번호**다. URL 쿼리 파라미터(`?code=...`)로 브라우저를 거쳐 전달되지만 안전한 이유가 세 가지다.

- **일회성** — 액세스 토큰 교환에 한 번 쓰이면 즉시 무효화.
- **짧은 유효 기간** — 보통 몇 분 이내.
- **교환 권한 제한** — client-secret을 가진 백엔드만 토큰으로 교환 가능.

## 카카오 설정 키 4종 (yaml)

| 키 | 역할 | 노출 시 위험 |
|---|---|---|
| `client-id` | 앱 식별자 (REST API Key). ③에서 어떤 앱의 요청인지 식별 | 낮음 |
| `client-secret` | ⑦ 토큰 교환 시 "등록된 백엔드"임을 증명 | **높음** — 앱 사칭 가능 |
| `redirect-uri` | ⑤에서 인가 코드를 돌려보낼 화이트리스트 주소. 등록값과 정확히 일치해야 함 | — |
| `admin-key` | 연결 끊기 등 관리자 권한 API | **최고** — 백엔드에서만 사용 |

`${KAKAO_CLIENT_SECRET:}` 형태는 "환경 변수를 쓰되 기본값 없음(필수 설정)"이라는 뜻.

## JWT Secret Key — 외부 발급이 아니라 직접 생성

Secret Key는 카카오 같은 외부에서 발급받는 게 아니라 **개발자가 직접 생성해 백엔드에만 보관**하는 서명용 열쇠다. `JWT_SECRET=your-secret-key-change-this-in-...` 같은 값은 키가 아니라 **가이드 문구**이며, 배포 전 반드시 무작위 값으로 교체해야 한다.

- 길이 — **HS256은 256비트(32자+), HS512는 512비트(64자+)**.
- 생성 — 언어 내장 암호화 유틸 사용. Java는 `SecureRandom` + Base64, Node는 `crypto.randomBytes(64)`.
- 보관 — `.env` 환경 변수로 분리, `.gitignore` 필수. 코드 하드코딩 금지.

```java
SecureRandom secureRandom = new SecureRandom();
byte[] key = new byte[64];   // 64바이트 = 512비트
secureRandom.nextBytes(key);
System.out.println(Base64.getEncoder().encodeToString(key));
```

### 곁다리 — `NoClassDefFoundError (wrong name)`

위 KeyGen을 CMD에서 `java KeyGen`으로 실행하면 소스에 `package kr.yeotaeho.api.util;` 선언이 있을 때 **클래스의 전체 경로 이름과 실행 이름이 불일치**해 실패한다. 일회용 유틸이면 패키지 선언을 지우고 컴파일하거나, 패키지 루트에서 `java kr.yeotaeho.api.util.KeyGen`으로 실행한다.

## 구현 체크리스트 (사이드 프로젝트 기준)

| 위치 | 항목 |
|---|---|
| 백엔드 | 카카오 API 통신(⑦~⑩) · User 엔티티에 **socialId unique** 필드 · JWT 유틸(생성/검증) · 더미 토큰을 실제 JWT로 교체 · 검증 필터(Spring `OncePerRequestFilter`) |
| 프론트 | 인가 코드 추출(`searchParams.get('code')`) · 콜백 요청 · 토큰 저장 · `Authorization: Bearer` 헤더 부착(Axios Interceptor) |

검증 필터의 에러 응답은 구분해야 한다 — **만료는 401 + 만료 코드**(프론트가 갱신 시도), **위변조는 401/403 + 보안 로그**.
