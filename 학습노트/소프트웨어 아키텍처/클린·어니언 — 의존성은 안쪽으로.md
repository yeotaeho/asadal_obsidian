# 클린·어니언 — 의존성은 안쪽으로

> [!summary] 한 줄 요약
> 두 구조의 규칙은 하나로 같다 — **의존성은 항상 핵심 비즈니스 로직을 향한다.** 중앙(Entity·Domain)이 가장 중요하고, 프레임워크·DB는 가장 바깥의 교체 가능한 껍데기다.

## Clean Architecture

Robert C. Martin이 정리한 구조. 동심원의 **중앙으로 갈수록 중요한 로직**이다.

```
┌─────────────────────────────┐
│ Framework / DB / Web        │
│   ┌─────────────────────┐   │
│   │ Interface Adapter   │   │
│   │  ┌───────────────┐  │   │
│   │  │ Use Case      │  │   │
│   │  │ ┌───────────┐ │  │   │
│   │  │ │ Entity    │ │  │   │
│   │  │ └───────────┘ │  │   │
│   │  └───────────────┘  │   │
│   └─────────────────────┘   │
└─────────────────────────────┘
```

의존 방향은 바깥 → 안쪽 한 방향뿐이다.

```
Spring MVC → OrderController → CreateOrderUseCase → Order Entity
```

목표는 **핵심 비즈니스 로직이 Spring에 의존하지 않게** 만드는 것이다.

## Onion Architecture

Clean과 매우 비슷하다. 양파처럼 Domain을 중심에 두고 계층이 감싼다.

```
Infrastructure  →  Application  →  Domain
```

Domain이 가장 안쪽이자 가장 중요한 중심이다.

## 세 구조의 관계

[[헥사고날 — 포트와 어댑터|Hexagonal]]·Clean·Onion은 **같은 문제의식의 다른 표현**이다. 셋 다 "도메인을 외부 기술로부터 지킨다"는 목표를 공유하며, 부르는 이름과 그림만 다르다. 대규모 서비스일수록 이 원칙의 값어치가 커진다.
