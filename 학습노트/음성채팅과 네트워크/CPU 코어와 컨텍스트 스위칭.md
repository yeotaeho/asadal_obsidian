# CPU 코어와 컨텍스트 스위칭

> [!summary] 한 줄 요약
> 코어는 **동시에 진짜로 실행할 수 있는 작업 수**를 정하고, RAM은 **만들 수 있는 프로세스/스레드 수**를 정한다. 코어 수보다 많은 작업은 OS가 시간을 잘게 쪼개 번갈아 돌린다(컨텍스트 스위칭) — 그래서 4코어에서도 프로세스 수백 개가 "동시에" 도는 것처럼 보인다.

## CPU 사양표에서 봐야 할 것

```
Intel Core i7 (예시)
  코어 수 (Cores): 8          ← 물리적으로 존재하는 독립 연산 장치
  스레드 수 (Threads): 16     ← 하이퍼스레딩/SMT로 코어 1개가 2개처럼 동작
```

- **코어** = CPU 칩 안의 물리적인 일꾼. 하드웨어다.
- **논리 스레드(논리 프로세서)** = 기술적으로 부풀린 일꾼 수. 이 CPU는 "한 번에 정확히 16개 작업을 물리적으로 동시에" 처리할 수 있다.

⚠️ 여기서 말하는 CPU "스레드"는 하드웨어 용어다. 소프트웨어의 스레드([[프로세스와 스레드]])와 이름만 같고 층위가 다르다 — CPU 스레드 16개는 "동시 실행 가능한 소프트웨어 스레드 수"의 상한일 뿐, 만들 수 있는 개수의 제한이 아니다.

## 스레드 16개인데 프로세스 300개가 도는 이유 — 컨텍스트 스위칭

작업 관리자를 보면 프로세스 200~300개, 스레드 수천 개가 돌고 있다. 어떻게?

```mermaid
flowchart LR
    OS["OS 스케줄러"]
    subgraph CORES["코어 4개 (물리 일꾼)"]
        C1["코어1"]
        C2["코어2"]
        C3["코어3"]
        C4["코어4"]
    end
    Q["수백 개의 프로세스/스레드"]
    Q --> OS
    OS -- "밀리초 단위로<br/>번갈아 배정" --> CORES
```

OS가 수천 개의 스레드를 밀리초 단위 시간 조각으로 쪼개, 코어에 넣었다 뺐다 하며 번갈아 실행한다. 워낙 빠르니 인간 눈에는 전부 동시에 도는 것처럼 보인다. 이 교체 작업이 **컨텍스트 스위칭**이다.

정리하면:

| 질문 | 답 | 결정 요인 |
|---|---|---|
| 동시에 **진짜** 실행되는 수 | 논리 스레드 수 (예: 16) | **CPU** |
| **만들 수 있는** 프로세스/스레드 수 | 수백~수천 | **RAM** (스레드마다 Stack 등 관리 메모리 소비) |

## 왜 개발자는 코어 수를 따지나 — 최적 효율

컨텍스트 스위칭은 공짜가 아니다. 그래서:

- **코어보다 스레드가 너무 많으면** (4코어에 1,000개): 일 바꾸는 비용(스위칭)이 커져 버벅인다
- **코어보다 너무 적으면** (16코어에 1개): 일꾼 15명이 논다 — 자원 낭비

경험 공식:

| 작업 성격 | 적정 스레드 수 |
|---|---|
| 연산 중심 (렌더링, 인코딩) | CPU 논리 스레드 수와 비슷하게 |
| 대기 중심 (웹 서버, DB, IO) | 논리 스레드 수의 2배~수배 (기다리는 시간이 많으니 여유 있게) |

## 프로젝트와의 연결

- 우리 서버의 **gunicorn 워커 4개**는 이 원리로 정해진 값이다 — 워커(프로세스) 수를 코어 수 근처로 맞춰 스위칭 낭비 없이 코어를 놀리지 않는 구성 ([[gunicorn 멀티워커 구조]]).
- 그런데 v4의 ICE 5초 블록은 이 산식을 무너뜨렸다: 워커가 4개뿐인데 세션 하나가 워커 하나를 5~10초씩 **통째로** 묶으니, 동시 4명이면 서버 전체가 응답 불능이 된다 ([[aiortc와 서버측 WebRTC]]). 코어가 아무리 남아돌아도 워커가 묶이면 소용없다.
