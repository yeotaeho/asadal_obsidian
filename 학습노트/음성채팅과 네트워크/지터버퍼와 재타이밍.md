# 지터버퍼와 재타이밍

> [!summary] 한 줄 요약
> **v4 가 오디오를 잃는 건 네트워크가 나빠서가 아니라, 중간에 시간을 다시 쓰기 때문이다.** 서버가 오디오 경로에 들어오는 순간 지터버퍼가 하나 더 생기고, 그 버퍼가 밀린 시간을 되찾을 수단이 없어 지연이 고이고 넘치면 발화 앞부분이 잘린다. 그런데 우리가 pts 를 새로 매기는 탓에 **잘렸다는 흔적조차 남지 않는다.**

## 왜 v4 에만 지터버퍼가 있나 — 릴레이 vs 종착지

지터(도착 간격의 출렁임)는 v3 에도 있었다. 모바일 실측 **633~772ms** 는 서버 밖 네트워크 물리라 구조와 무관하게 존재한다.

차이는 지터가 **누구 문제가 되느냐**다.

| | 우리 서버 (v4) | OpenAI Realtime |
|---|---|---|
| 오디오를 받아서 | **다음 WebRTC 홉으로 다시 내보낸다** | 모델 입력으로 소비한다 |
| 출력 의무 | `recv()` 가 20ms마다 프레임 하나를 계속 내놔야 한다 | 없음 |
| 그래서 필요한 것 | **재생 버퍼** (유한 → 넘치면 폐기) | 단순 누적으로 충분 |

700ms 뭉치가 **종착지**에 도착하면 그냥 "700ms치가 입력에 추가됨"이다. 버릴 이유가 없다 — 맞춰야 할 하류 시계가 없기 때문이다.

우리는 하류 시계가 있다. 그래서 버퍼가 필요하고, 버퍼는 유한하고, 유한하면 넘친다. **v3 는 이 구간 자체가 존재하지 않았다.**

> [!warning] 표현 정정
> 이전에 "OpenAI 수신 버퍼가 지터를 흡수하도록 튜닝돼 있다"고 적은 적이 있는데 근거 없는 추측이었다. 정확히는 **튜닝 차이가 아니라 역할의 비대칭**이다. OpenAI 는 흡수할 필요가 없고, 우리는 있다.

## 우리 버퍼의 실제 파라미터

`AudioProxyTrack` (`v4/audio_tracks.py`) 이 `deque` 로 손수 만든 물건이다. aiortc 에는 이 방향의 NetEq 이 없다.

| 항목 | 값 | 비고 |
|---|---|---|
| 프리버퍼 목표 | 80ms (4프레임) | `target_buffer_ms` |
| 상한 | **960ms** (48프레임) | 2026-08-21 상향 (구 320ms) |
| 초과 시 | `popleft()` — **가장 오래된 것부터 폐기** | `_reader_loop` |
| 언더플로 타임아웃 | 100ms | 그 뒤 20ms 침묵 프레임 1개 방출 |
| 송출 페이싱 | **1배속 고정** | `_pace_playout`, 우리 서버 `time.monotonic()` 기준 |
| 배속 가속 | 4배속 — **게이트 방출 경로에만** | `_DRAIN_SPEEDUP`, 지터 백로그엔 안 붙는다 |

## 빚을 못 갚는 구조 — 리베이스

```python
target_time = self._playout_started_at + self._playout_elapsed_sec
sleep_sec = target_time - now
if sleep_sec > 0:
    await asyncio.sleep(sleep_sec)
elif sleep_sec < -0.25:
    self._playout_started_at = now - self._playout_elapsed_sec   # ← 장부를 지운다
```

언더플로 1회마다 **벽시계 +100ms, 방출 +20ms** — 차이가 80ms씩 벌어진다.

| 언더플로 | 벽시계 | 방출 | 밀린 양 | 리베이스 |
|---|---|---|---|---|
| 1회 | 100ms | 20ms | 100 → 80 | — |
| 2회 | 200ms | 40ms | 180 → 160 | — |
| **3회** | **300ms** | **60ms** | **260** | ✅ |
| 4~6회 | 600ms | 120ms | 240 → 220 | — |
| **7회** | **700ms** | **140ms** | **320** | ✅ |

**첫 리베이스는 3회째(300ms), 이후 4회마다(400ms).**

리베이스가 지우는 건 오디오가 아니라 **빚**이다. "300ms 동안 60ms만 내보냈으니 240ms 빨리 빼내야 한다"는 장부를 탕감한다. 그러면 뒤늦게 도착한 뭉치를 **1배속으로만** 내보내게 되고, 그만큼이 버퍼에 눌러앉는다.

**이 단계의 결과는 손실이 아니라 영구 지연이다.** 오디오는 늦게 올 뿐 사라지지 않았다.

## 수위 래칫 — 한번 오르면 안 내려온다

```
수위 L, 지터 갭 G 가 왔을 때
  갭 동안:   버퍼는 실시간으로 빠진다 → L-G   (L<G 면 바닥, 그만큼 침묵 방출)
  뭉치 도착: +G
  결과 수위 = max(L, G)
```

무한 누적은 아니지만 **지금까지 겪은 최대 지터만큼 고이고 절대 줄지 않는다.** 1배속밖에 없어 되돌릴 수단이 없기 때문이다. 그게 상시 지연으로 남는다.

## 진짜 손실 — 앞부분부터 잘린다

수위가 상한을 넘는 순간 `_reader_loop` 이 `popleft()` 한다. **뒷부분이 아니라 앞부분이다.**

400ms 뭉치(20프레임)가 상한 300ms(15프레임)에 도착하면 **5프레임(100ms)이 앞에서부터 폐기**된다. 상한을 320 → 960 으로 올린 이유이고, 그럼에도 **만수위 47/48** 이 관측됐다 — 지터가 가끔 880ms를 넘는다.

## 재타이밍 — 시간 좌표계를 갈아끼운다

```python
frame.pts = self._next_pts
self._next_pts += max(1, samples)     # 무조건 +20ms
```

`_retime_frame()` 은 프레임이 언제 도착했든, 원본 RTP 타임스탬프가 뭐였든 **읽지도 않고** 직전 프레임 + 정확히 20ms 로 찍는다.

| | 의미 |
|---|---|
| **원본 pts (v3)** | 이 오디오는 **언제 녹음됐나** |
| **우리 pts (v4)** | 이 오디오는 **내가 몇 번째로 내보냈나** |

전혀 다른 정보고, 두 번째에서 첫 번째를 복원할 방법은 없다. 결과적으로 우리 출력 스트림에는 **구조적으로 구멍이 존재할 수 없다.**

### v3 와 나란히 놓으면

브라우저가 `[안녕][하세][요__]` 를 보냈는데 첫 프레임이 유실된 경우.

```
v3 — 브라우저 → OpenAI 직결
  도착:   (없음)   [하세]   [요__]
  pts:     100      200      300
                     ↑ 100 자리가 비었다 → 수신측이 "20ms 누락"을 안다

v4 — 우리가 재타이밍
  도착:   (없음)   [하세]   [요__]
  우리 pts:         100      200
                     ↑ 빈틈없음 → 수신측은 끊긴 줄을 모른다
```

**우리가 구멍 정보를 파괴한다.**

## 그래서 손실이 세 갈래로 생긴다

| 경로 | 내용 |
|---|---|
| **① 침묵의 둔갑** | 언더플로 침묵은 "데이터를 모르겠다"인데, 재타이밍이 이를 **"이 시각에 사용자가 말을 안 했다"** 는 사실 주장으로 바꾼다 |
| **② 시계 드리프트** | `_pace_playout` 은 **우리 서버 시계**, 브라우저는 **자기 샘플 클록**. 수십 ppm씩 어긋난다. 브라우저가 빠르면 수위 단조 증가 → 폐기, 느리면 언더플로 → 침묵. 정석(NetEq)은 시간축 신축으로 흡수하지만 우리 조절 수단은 **버리기뿐** |
| **③ 드레인 버스트** | 4배속 구간은 페이싱 5ms / pts 20ms. 1.2초 내용을 300ms에 몰아 보내므로 **수신측 버퍼가 뭉치보다 작으면 앞부분을 버린다** — 코드 주석의 *"마지막 두 어절만 전사"* 의심 원인 |

## 가장 나쁜 결과 — 손실이 손실로 보이지 않는다

`popleft()`(앞부분 폐기)와 재타이밍이 만나면.

```
브라우저가 말한 것:  [안녕][하세][요__][반갑][습니][다__]
버퍼 초과로 앞 2개:    ✗     ✗
우리가 내보내는 것:  [요__][반갑][습니][다__]
붙는 pts:             100   200   300   400        ← 빈틈없음
```

OpenAI 가 받는 건 **"요 반갑습니다"라는, 처음부터 그랬던 것처럼 보이는 완결된 오디오**다.

**"AI 가 말을 못 알아듣는다"의 정체가 이것이다.** 오디오가 끊겨서 인식을 못 하는 게 아니라, **말이 되는 다른 오디오로 조용히 바뀌어서** 그걸 정확히 인식하는 것이다. 경고도 안 뜨고 `dropped_frames` 카운터 말고는 로그에도 안 남는다.

## 고칠 수 있나 — 물리 한계가 아니라 설계 선택이다

WebRTC 는 실시간보다 빨리 보내는 걸 막지 않는다. **드레인 4배속이 이미 그걸 하고 있다.** 같은 수단을 지터 백로그에도 쓰면 된다.

| 방안 | 내용 | 비용 | 해결 |
|---|---|---|---|
| **A. 적응형 배속** | 수위 > 목표면 돌아올 때까지 N배속 페이싱 | **~10줄** | 지터 폐기 대부분 + 상시 지연 |
| **B. 리베이스 제거** | `-0.25` 탕감을 없애고 실제로 따라잡게 | ~3줄 | A의 부분집합 |
| **C. 재페이싱 제거** | 업링크는 오는 대로 흘려보낸다 (v3 형태) | 게이트와 공존 불가 | 전부 |
| **D. NetEq / WSOLA** | 시간축 신축으로 정석 흡수 | 라이브러리·CPU | 전부 (게이트 유지) |

**A 가 압도적으로 싸다.** 빚을 실제로 갚아 수위를 목표치로 되돌리면 상시 지연이 사라지고 **헤드룸이 회복돼** 다음 뭉침을 받을 자리가 생긴다.

## 정직하게 — 확실한 것과 추측

| 주장 | 근거 |
|---|---|
| 우리가 pts 를 새로 매기고 원본을 버린다 | ✅ 코드 |
| 출력에 구멍이 생길 수 없다 | ✅ 코드 |
| 드리프트 보상·시간축 신축이 없다 | ✅ 코드 (조절 수단이 `popleft` 뿐) |
| v3 는 브라우저 RTP 타임스탬프가 OpenAI 까지 그대로 간다 | ✅ 서버가 오디오 경로 밖 |
| OpenAI 가 타임스탬프 구멍을 PLC 로 은닉한다 | 🔸 **추측** — 표준 WebRTC 수신기의 통상 동작이나 미확인 |

확실한 건 **"우리가 구멍 정보를 파괴한다"** 까지다. 그 정보로 상대가 뭘 하든, 없는 것보다는 낫다는 게 논지다.
