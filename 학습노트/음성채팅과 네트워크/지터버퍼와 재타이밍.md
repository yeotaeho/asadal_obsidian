# 지터버퍼와 재타이밍

> [!summary] 한 줄 요약
> 지터버퍼는 **불규칙하게 도착한 오디오를 규칙적으로 내보내기 위한 대기실**이다. 대기실이 유한한 순간 "언제 무엇을 버릴 것인가"가 설계 문제가 되고, 시간을 다시 쓰는 순간 **버렸다는 사실 자체가 지워진다.** v4가 말을 못 알아듣는 이유가 여기 있다.

## 지터란 무엇인가

오디오는 통째로 흐르지 않는다. **20ms짜리 조각**으로 잘려 UDP 패킷 하나씩 날아간다(초당 50개).

보내는 쪽은 정확히 20ms마다 보낸다. 그런데 받는 쪽에 그 간격 그대로 도착하지 않는다.

```
보낸 간격:  20  20  20  20  20  20  20  20        (일정)
받은 간격:  18  25  3   40  700 2   2   2   ...   (제멋대로)
                        ↑ 뭉쳐서 한꺼번에 도착
```

이 **도착 간격의 출렁임이 지터**다. 라우터 큐잉, 무선 재전송, 캐리어 스케줄링 — 원인은 서버 밖 네트워크 물리라 코드로 없앨 수 없다. 모바일 실측에서 **633~772ms** 까지 나온다.

문제는 **재생은 반드시 일정해야 한다**는 것이다. 20ms 오디오를 20ms 동안 재생해야 소리가 정상이다. 불규칙한 도착과 규칙적인 재생 사이의 간극을 메우는 장치가 **지터버퍼**다.

```
[불규칙 도착] → [지터버퍼 = 대기실] → [일정한 재생]
```

## 깊이의 딜레마 — 벗어날 수 없는 트레이드오프

대기실을 얼마나 깊게 팔 것인가. 이 하나가 지터버퍼 설계의 전부다.

| 얕게 | 깊게 |
|---|---|
| 지연 짧음 ✓ | 지연 김 ✗ |
| 조금만 늦어도 재생할 게 없다 → **언더플로(끊김)** ✗ | 웬만한 출렁임을 다 흡수 ✓ |

**둘 다 좋게 만들 방법은 없다.** 깊이를 늘리면 그만큼 오디오가 대기실에 앉아 있는 시간이고, 그게 곧 통화 지연이다. 그래서 지터버퍼는 항상 "지금 네트워크가 얼마나 출렁이나"를 보고 깊이를 조절해야 한다 — 고정 깊이는 반드시 어느 한쪽에서 진다.

## 누가 지터버퍼를 필요로 하나 — 릴레이 vs 종착지

여기서 자주 헷갈리는 게 있다. **지터가 있다고 모두가 버퍼를 필요로 하는 건 아니다.** 기준은 하나다.

> 받은 오디오를 **다시 실시간으로 내보내야 하는가?**

| | 필요한 쪽 (릴레이) | 필요 없는 쪽 (종착지) |
|---|---|---|
| 받아서 하는 일 | 다음 홉으로 **다시 내보낸다** | 소비한다 (재생·인식) |
| 출력 의무 | 20ms마다 프레임 하나를 계속 내놔야 한다 | 없음 |
| 700ms 뭉치가 오면 | 대기실에 쌓아두고 20ms씩 빼내야 한다 | 그냥 "700ms치가 추가됨". 버릴 이유 없음 |

**대기실이 필요 없으면 넘칠 일도 없다.** 이게 v3와 v4의 근본 차이다.

```
v3:  [브라우저] ═══════════════> [OpenAI]     버퍼 1개 (종착지)
v4:  [브라우저] ══> [우리 서버] ══> [OpenAI]   버퍼 2개 (릴레이 + 종착지)
                     ↑ 여기가 새로 생긴 대기실
```

버퍼가 하나 늘었다는 건 **버릴 기회가 하나 늘었다**는 뜻이다. 서버를 오디오 경로에 끼우면 자동으로 따라오는 비용이고, [[aiortc와 서버측 WebRTC]]의 ICE 5초와 같은 성격이다 — 참여자가 되는 대가.

> [!note] 흔한 오해
> "OpenAI 쪽 버퍼가 잘 튜닝돼 있어서 v3는 괜찮았다"고 설명하기 쉬운데, 튜닝 차이가 아니다. **종착지는 애초에 흡수할 필요가 없다.**

## 넘칠 때 무엇을 버리나 — 하필 앞부분

대기실이 꽉 차면 뭔가는 버려야 한다. 실시간 오디오에서 표준 선택은 **가장 오래된 것부터**(drop-oldest)다. 지금 이 순간의 대화가 3초 전 대화보다 가치 있기 때문이다.

그런데 음성에서 "가장 오래된 것"은 **발화의 앞부분**이다.

```
말한 것:   안녕하세요 반갑습니다
버려진 것: ▓▓▓▓
남은 것:        하세요 반갑습니다
```

음성 인식에서 앞부분 손실은 특히 나쁘다. 뒷부분이 잘리면 "말이 중간에 끊겼다"고 알아채지만, 앞부분이 잘리면 **여전히 말이 되는 다른 문장**이 되기 때문이다.

## 시계는 언제나 두 개다 — 드리프트

지터만 문제가 아니다. 더 조용하고 확실한 문제가 있다.

보내는 쪽은 **자기 사운드카드의 샘플 클록**으로 오디오를 만들고, 받는 쪽은 **자기 시계**로 재생한다. 이 둘은 절대 정확히 같지 않다 — 보통 수십 ppm(백만분율) 어긋난다.

백만분의 오십은 무시해도 될 것 같지만, **한 방향으로만 쌓인다**는 게 핵심이다.

```
보내는 쪽이 아주 조금 빠르면  → 대기실이 계속 차오른다 → 언젠가 반드시 넘친다
보내는 쪽이 아주 조금 느리면  → 대기실이 계속 비어간다 → 언젠가 반드시 끊긴다
```

통화가 길수록 확실해진다. 그래서 **지터버퍼는 원리적으로 적응형이어야 한다.** 고정 깊이 + 넘치면 버리기 조합은 "드리프트를 폐기로 갚는" 것이고, 그 청구서는 사용자 발화로 날아온다.

## 정석은 시간을 늘리고 줄인다 — NetEq

그럼 적응형 지터버퍼는 밀리거나 남는 시간을 어떻게 정산할까. 브라우저가 쓰는 **NetEq**(WebRTC 내장)의 답은 이렇다.

| 상황 | 동작 | 뜻 |
|---|---|---|
| 대기실이 너무 참 (지연 과다) | **accelerate** | 오디오를 **살짝 빨리** 재생해 깊이를 줄인다 |
| 대기실이 비어감 (도착 지연) | **expand** | 오디오를 **살짝 늘여** 다음 패킷이 올 시간을 번다 |
| 패킷이 아예 유실 | **손실 은닉(PLC)** | 앞뒤 파형으로 그럴듯하게 메운다 |

핵심은 **피치를 안 바꾸고 길이만 바꾸는 것**이다(WSOLA 계열). 배속 재생처럼 음이 높아지면 못 쓰기 때문이다. 이게 NetEq이 복잡한 이유이자, 지터버퍼가 "그냥 큐"가 아닌 이유다.

**단, 이 복잡함이 필요한 조건이 있다 — 하류에 사람 귀가 있을 때다.** 하류가 기계(음성 인식 모델)라면 이야기가 달라진다. 아래에서 다시 본다.

## 재타이밍 — 타임스탬프에 무엇이 담겨 있나

여기부터가 두 번째 주제다. 오디오 조각마다 **타임스탬프**가 붙는데, 이게 무슨 정보인지가 결정적이다.

| | 담긴 뜻 |
|---|---|
| **원본 타임스탬프** (보낸 쪽이 찍음) | 이 오디오는 **언제 녹음됐나** |
| **재타이밍한 타임스탬프** (중계자가 다시 찍음) | 이 오디오는 **내가 몇 번째로 내보냈나** |

전혀 다른 정보고, 두 번째에서 첫 번째를 복원할 방법은 없다.

### 구멍도 정보다

원본 타임스탬프를 그대로 넘기면, 유실은 **번호의 구멍**으로 남는다.

```
정상:   100  120  140  160     연속
유실:   100  ___  140  160     ← 120 자리가 비었다 = "20ms 없어졌다"
```

받는 쪽은 이 구멍을 보고 손실 은닉을 하거나, 최소한 **끊겼다는 사실을 안다.**

그런데 중계자가 번호를 새로 매기면 이렇게 된다.

```
유실 후 재타이밍:   100  120  140     ← 빈틈없음
```

**구멍이 사라졌다.** 유실은 그대로인데 흔적만 지워졌다. 받는 쪽 입장에서 이 스트림은 처음부터 완전했던 오디오다.

### 손실이 손실로 보이지 않는다

drop-oldest와 재타이밍이 만나면 결과가 이렇다.

```
말한 것:      안녕하세요 반갑습니다
앞부분 폐기:  ▓▓▓▓
받는 쪽이 보는 것:  "하세요 반갑습니다"   ← 완결된 문장. 잘린 흔적 없음
```

**"AI가 말을 못 알아듣는다"의 정체가 대개 이것이다.** 인식에 실패한 게 아니라, **말이 되는 다른 오디오를 정확히 인식**한 것이다. 오류가 아니라 정답이므로 경고도 뜨지 않는다.

중계자를 하나 끼울 때 진짜로 잃는 건 오디오가 아니라 **"오디오를 잃었다는 정보"** 다.

## v4에 이것이 어떻게 나타났나

개념이 실제 코드에서 어떤 모양이었는지 (`v4/audio_tracks.py`).

**1. 밀린 시간을 갚지 않고 지웠다.** 도착이 늦어 침묵으로 때우면 "내보낸 양"이 "흐른 시간"보다 적어지며 빚이 쌓인다. 그런데 빚이 250ms를 넘으면 기준 시각을 현재로 리셋해 **장부에서 지워버렸다.** 갚을 방법(accelerate)이 없으니 지운 것인데, 결과적으로 늦게 온 오디오가 1배속으로만 빠진다.

**2. 그래서 수위가 래칫으로 굳었다.** 지터 갭 G가 오면 결과 수위는 `max(기존 수위, G)`다. 한 번 오르면 내려올 수단이 없어 **지금까지 겪은 최대 지터**가 상시 지연으로 눌러앉는다.

**3. 상한에 닿으면 앞부분부터 버렸다.** 상한을 320ms → 960ms로 올리고도 **만수위 47/48**이 관측됐다.

**4. 그리고 재타이밍이 흔적을 지웠다.** 매 프레임 무조건 +20ms로 번호를 다시 매기므로 출력에 구멍이 생길 수 없다.

## 배속으로 NetEq을 대신할 수 있을까

정석대로면 시간축 신축을 구현해야 한다. 그런데 우리 상황에는 빠져나갈 구멍이 있어 보였다.

```
업링크:   사용자 → [우리 서버] → OpenAI 모델    ← 하류가 기계. 귀 없음
다운링크: OpenAI → [우리 서버] → 브라우저      ← 브라우저에 NetEq 내장
```

업링크 하류는 기계다. 실시간보다 빨리 밀어넣어도 타임스탬프가 정상 간격이면 원래 속도로 재구성되니 **피치가 높아질 걱정이 없다.** 그러니 밀린 빚은 신축이 아니라 **그냥 빨리 내보내면** 갚을 수 있어 보인다.

실제로 구현해 측정했다.

| 700ms 지터 | 1배속 | 4배속 |
|---|---|---|
| 버퍼 체류 지연 | 260ms | **0ms** ✓ |
| 언더플로 침묵 | 11개 | **508개** ✗ |
| **폐기 프레임** (1200ms 지터) | 600건 | **600건 — 동일** ✗ |

**지연은 줄지만 폐기는 하나도 안 준다.** 그리고 폐기야말로 애초에 없애려던 것이었다.

#### 왜 폐기가 안 주나

폐기는 **뭉치 하나가 버퍼 상한보다 클 때** 생긴다. 그 순간 버퍼는 이미 비어 있다 — 직전 공백 동안 다 빠져나갔기 때문이다. 자리가 없어서 버리는 게 아니라 **한 번에 들어온 양이 그릇보다 커서** 버리는 것이다.

빨리 빼내는 건 이미 비어 있는 그릇을 더 비우는 일이라 아무것도 바꾸지 못한다. 그릇을 키우거나(상한 상향) 들어오는 양을 줄이는 것 말고는 방법이 없다.

#### 그리고 수위는 쿠션이었다

수위를 "없애야 할 지연"으로 봤는데, 실제로는 **다음 뭉치까지 버틸 재고**다. 바닥까지 비우면 미세한 출렁임마다 소스가 말라 언더플로가 난다 — 침묵 프레임이 11개에서 508개로 늘어난 이유다.

버퍼가 지터를 흡수하는 일을 그만둔 셈이다.

#### 교훈

**지터는 어딘가에서 반드시 대가를 치른다.** 페이싱만으로는 그 대가를 *폐기 ↔ 침묵 ↔ 지연* 사이에서 옮길 수 있을 뿐 없앨 수 없다.

없애려면 **없는 시간을 만들어내야** 하고, 그게 정확히 시간축 신축이 하는 일이다 — 오디오를 늘여서 다음 패킷이 올 시간을 벌고, 줄여서 쌓인 재고를 삼킨다. **NetEq이 복잡한 건 우회로가 없어서다.**

> [!note] 이 노트에서 두 번 틀렸던 자리
> ① 원래 이 절은 "하류에 사람 귀가 없으니 배속으로 대신할 수 있다"는 결론이었다. 피치 전제는 맞았지만 **폐기가 안 준다**는 걸 안 봤다.
> ② 그 뒤엔 반대로 "배속이 발화를 전멸시킨다"고 적었다. 언더플로 침묵을 20ms 간격으로 오해해 공백 525ms를 26프레임으로 셌는데, 실제로는 **타임아웃(100ms)마다 1개**라 6프레임이다. 게이트 임계(연속 20)에 닿지 않아 조각남은 없었다.
> 두 번 다 **조건 하나를 확인하고 다른 조건을 안 본** 실수다.

## 정직하게 — 확실한 것과 추측

| | |
|---|---|
| 중계자가 타임스탬프를 다시 쓰면 유실 흔적이 사라진다 | ✅ 원리적으로 확실 |
| 종착지는 지터버퍼가 필요 없다 | ✅ 출력 의무가 없으므로 |
| 고정 깊이 버퍼는 드리프트를 폐기로 갚는다 | ✅ 원리적으로 확실 |
| OpenAI가 타임스탬프 구멍을 받으면 손실 은닉을 한다 | 🔸 **추측** — 표준 WebRTC 수신기의 통상 동작이나 미확인 |

마지막 줄은 확인하지 못했다. 확실한 건 **"구멍 정보를 파괴한다"** 까지고, 받는 쪽이 그 정보로 뭘 하든 없는 것보다는 낫다는 게 논지다.
