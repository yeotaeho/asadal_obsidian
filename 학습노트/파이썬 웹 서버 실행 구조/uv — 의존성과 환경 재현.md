# uv — 의존성과 환경 재현

> [!summary] 한 줄 요약
> uv는 Python 프로젝트의 패키지 관리 도구다. 핵심 값어치는 설치 속도보다 **`uv.lock`으로 개발 PC와 운영 서버의 실행 환경을 똑같이 재현**하는 데 있다.

## 두 파일의 역할이 다르다

```
project/
├── pyproject.toml   ← 어떤 라이브러리를 쓰는가 (의도)
└── uv.lock          ← 정확히 어떤 버전이 깔리는가 (사실)
```

```toml
# pyproject.toml — 느슨한 선언
dependencies = ["fastapi", "httpx", "sqlalchemy"]
```

`uv.lock`은 여기에 더해 **설치될 정확한 버전까지 못 박는다**. 그래서 아래 경로 전체에서 같은 실행 환경이 만들어진다.

```
개발자 PC → uv.lock → Docker 이미지 → 운영 서버
```

`uv add fastapi`처럼 추가하면 두 파일이 함께 갱신된다.

## pip와의 자리 비교

생태계 대응을 보면 위치가 바로 잡힌다.

| 언어 | 도구 |
|---|---|
| JavaScript | npm / pnpm / yarn |
| Python | pip / Poetry / **uv** |

`pip install` 중심 환경 대신 uv를 쓰는 이유는 **빠르고 lock 관리가 간단하기 때문**이다. `requirements.txt`만 쓰는 프로젝트는 버전이 느슨해서 "내 PC에선 되는데 서버에선 안 된다"가 나오기 쉽다.

## 왜 이 폴더에 두는가

이 폴더의 나머지 노트가 **"앱이 어떻게 실행되는가"** 를 다룬다면, uv는 그 앞단인 **"어떤 코드가 실행되는가"** 를 고정한다. 실행 구조를 아무리 정확히 파악해도 **서버에 깔린 라이브러리 버전이 다르면 재현이 안 된다**.

같은 함정을 컨테이너 쪽에서 겪은 기록이 있다 — `.env`는 컨테이너 시작 시에만 읽히고 `docker compose up -d`는 이미지를 재빌드하지 않는다 → [[리버스 프록시 프리픽스 라우팅과 dev·운영 컨테이너 분리]]. **lock 파일과 이미지 재빌드는 같은 문제의 두 얼굴**이다.
