# uvicorn과 gunicorn

> [!summary] 한 줄 요약
> **uvicorn은 요청을 실제로 처리하는 서버, gunicorn은 그 서버를 여러 개 띄우고 감시하는 관리자**다. 둘 다 별도 프로그램이 아니라 **우리 앱과 같은 프로세스 안에서 도는 파이썬 패키지**다.

## FastAPI 는 서버가 아니다

`app.py` 에 이렇게 써놓아도 그건 **함수 정의일 뿐**이다.

```python
@app.post("/ask")
async def ask(...): ...
```

누군가 포트를 열고, 들어온 HTTP 바이트를 해석하고, 그 함수를 대신 불러주고, 반환값을 다시 HTTP 로 포장해야 한다. **FastAPI 는 "요청이 오면 무엇을 할지"만 정의하는 프레임워크**이고, "어떻게 받을지"는 서버의 몫이다.

그 둘 사이의 약속이 **ASGI** 규약이다.

```
[FastAPI]  ←── ASGI 규약 ──→  [uvicorn]
 무엇을 할지                    어떻게 받을지
```

규약이 있어서 서버를 갈아끼워도 앱 코드는 한 줄도 안 바뀐다.

> [!note] WSGI 와 ASGI
> WSGI 는 동기 시대의 규약이라 `async def` 를 다루지 못한다. gunicorn 은 원래 WSGI 서버라서, **FastAPI 같은 ASGI 앱을 gunicorn 혼자서는 돌리지 못한다.** 아래 `worker_class` 설정이 그래서 필요하다.

## uvicorn — 실제로 일하는 쪽

`pip install uvicorn` 으로 설치하는 **평범한 파이썬 패키지**다. 파이썬에 내장된 엔진도, 외부 프로그램도 아니다.

```
python3.11 이 uvicorn 을 실행
  → uvicorn 이 포트 소켓을 염
  → 요청이 오면 HTTP 를 해석
  → 우리 app 객체를 import 해서 해당 함수를 호출
  → 반환값을 HTTP 응답으로 만들어 보냄
```

**우리 앱 코드와 같은 인터프리터, 같은 프로세스 안에서 돈다.** 그래서 우리 코드가 이벤트 루프를 막으면 uvicorn 도 같이 멈춘다 ([[이벤트 루프]]).

uvicorn 하나는 프로세스 하나다. 그 안에서 **이벤트 루프가 수백~수천 개 요청을 번갈아 처리**하므로, 프로세스가 하나여도 동시 접속을 감당한다 → [[동시성 층위 — 워커·스레드·작업]]

## gunicorn — 관리만 하는 쪽

**요청을 잘 처리하는 게 아니라 일꾼을 관리한다.** 워커 프로세스를 N개 fork 하고, 죽으면 되살리고, 무중단 재시작을 해준다.

**요청을 분배하지는 않는다.** 워커들이 같은 포트를 다같이 듣고 있다가 먼저 집는 놈이 임자다. 큐는 OS 커널이 갖고 있다 → [[gunicorn 멀티워커 구조]]

## 둘을 합치는 지점

```python
# gunicorn.conf.py
worker_class = "uvicorn.workers.UvicornWorker"
```

**"gunicorn 이 관리하되, 일꾼 하나하나는 uvicorn 규격으로 돌려라"** 는 선언이다. 공장장(gunicorn)이 요리사(uvicorn)를 여러 명 고용한 구조가 된다.

```
gunicorn (마스터) ─┬─ uvicorn 워커 1   (프로세스, 이벤트 루프 1개)
                   ├─ uvicorn 워커 2
                   └─ uvicorn 워커 N
```

gunicorn 만이 유일한 방법은 아니다. `uvicorn --workers N` 도 프로세스를 여러 개 띄운다. 다만 프로세스 감시·무중단 재시작 같은 운영 기능은 gunicorn 쪽이 두텁다.

## 왜 굳이 여러 개를 띄우나

파이썬은 GIL 때문에 **프로세스 하나가 CPU 코어 하나만** 쓴다. 8코어 서버에서 uvicorn 하나만 돌리면 7코어가 논다 ([[CPU 코어와 컨텍스트 스위칭]]).

대신 대가가 있다. 워커는 독립된 프로세스라 **메모리를 공유하지 않는다.** 세션 상태를 메모리에 들고 있으면 다른 워커가 그 세션을 모른다 — v4 가 실제로 물린 지점이다 ([[gunicorn 멀티워커 구조]]의 함정 ③).

## 우리 프로젝트의 실제 구성 (2026-08-13 서버 실측)

| 구분 | 실행 방식 | 프로세스 |
|---|---|---|
| dev Chat App (9010) | `uvicorn app:app` **단독** (`kss_app.service`) | 1개, 루프 1개 |
| 이 서버의 다른 gunicorn 들 | `gunicorn --workers 2` (명령줄 지정) | 마스터 1 + 워커 2 |
| 운영 Chat App | gunicorn + UvicornWorker | 워커 수 **미확인** |

**dev 는 gunicorn 을 쓰지 않는다.** 그래서 워커 개념 자체가 없고, 멀티워커에서만 터지는 버그(루프 불일치, 워커 간 메모리 비공유)를 **dev 에서는 구조적으로 재현할 수 없다.** 운영 배포가 사실상 첫 검증이 된다.

## `gunicorn.conf.py` 의 함정

```python
worker = Config.APP_WORKERS      # ← 단수. gunicorn 설정 이름은 workers
```

gunicorn 은 설정 파일에서 **아는 이름만 골라 적용하고 모르는 이름은 조용히 무시한다.** `worker` 는 유효한 설정이 아니므로 이 줄은 아무 일도 하지 않고, `workers` 는 기본값 **1** 이 된다.

지금은 무해하다 — 실제 구동이 명령줄 `--workers 2` 로 이뤄지고 **명령줄이 설정 파일보다 우선**하기 때문이다. 다만 gunicorn 은 `-c` 를 안 줘도 **작업 디렉터리의 `gunicorn.conf.py` 를 자동으로 읽으므로**, 누가 명령줄 플래그를 빼는 순간 워커가 1개가 된다. 조용히 성능이 반토막 나고 아무도 모른다.
